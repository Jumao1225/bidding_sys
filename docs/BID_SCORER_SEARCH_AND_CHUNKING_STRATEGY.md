# 智能标书语义检索与三层金字塔分块策略设计方案 (Bid Scorer Search & Chunking Strategy)

> **创建日期**：2026-07-30  
> **文档状态**：设计完成，指导实施  
> **适用模块**：`BidScorerAgent` / `ExtractorService` / `RAGService` / `RoutingService`

---

## 1. 背景与核心痛点

在基于 LLM 与 RAG 的智能投标评分系统中，传统的**固定字符切片（如每 500 字一切）**和**单一向量盲搜**暴露了三大致命隐患：

1. **表格被拦腰切断**：业绩一览表、分项报价表被按字符硬生生斩断，导致表头丢失、数据变成“废文本”。
2. **“标书里有，AI 却扣分”的尴尬**：由于向量检索未命中包含表格的微小切片，大模型断定“正文未找到相关证据”，导致客观存在的业绩/资质被错误判为 0 分。
3. **Context 爆炸与盲目堆叠**：若将几十万字的标书直接扔给大模型，会导致 Token 消耗爆炸、响应极其缓慢且大模型产生严重的“迷失在中间 (Lost in the Middle)”幻觉。

---

## 2. 核心架构选型 — 双轨协同架构 (Hybrid Dual-Engine Architecture)

为了彻底解决上述痛点，系统采取 **“主动要素萃取台账 + 向量语义检索与举证” 双轨协同机制**：

```
                      ┌───► 结构化要素台账矩阵 ───► 自动核验硬指标（业绩/资质/报价表单）
                      │     (出现即得分，精度100%)
投标文件 ───► 解析分块 ┤
                      │
                      └───► 向量数据库 (Hybrid RAG) ───► 语义搜索软方案（施工/预案）+ 原文举证
```

| 评估维度 | 结构化要素台账矩阵 | 向量数据库 (Hybrid RAG) |
| :--- | :--- | :--- |
| **打分对象** | 开标一览表、业绩一览表、商务偏离表、人员证书、资质文件 | 施工方案、应急预案、质量保证措施、服务承诺 |
| **处理逻辑** | 按目录大章提取结构化 JSON，**只要标书中存在即判定给分** | 结合语义相似度 + 关键字查漏，检索特定方案段落 |
| **主要职责** | **负责硬指标打分** | **负责软方案打分 + 物理页码原文举证溯源** |

---

## 3. 5 重智能标书语义检索策略矩阵 (5-Layer Hybrid Retrieval Strategy)

针对软方案与复杂条款的检索，设计 5 重递进式检索策略，确保检索高召回与零噪音：

```
                            ┌─ [硬指标评分项] ──► 策略1: 结构化要素表单直连 (精度100%)
                            │   (业绩/资质/报价)
评分细则 (Scoring Rule) ───┤
                            │   (施工/预案/方案) ──► 策略2: 章节元数据范围过滤 (Filter)
                            └─ [软指标评分项] ──┤
                                                ├─► 策略3: 评分项 Query 同义扩充 (Rewrite)
                                                ├─► 策略4: 向量 + 关键字 (Hybrid + RRF)
                                                └─► 策略5: 父子切片上下文还原 (Parent-Child)
```

### 3.1 第一层：评分项意图分流 (Intent Routing)
- **硬指标评分项**（业绩、资质证书、报价表）：直连结构化要素台账，无需向量检索。
- **软指标/主观评分项**（施工方案、应急预案、培训计划）：路由至 2~5 层语义检索通道。

### 3.2 第二层：章节元数据精确拦截 (Metadata Range Filtering)
- **原理**：结合 MinerU 目录 (TOC) 白名单提取的大章名，在检索时加入 `metadata.section_title` 过滤。
- **示例**：评分项要求查看 *“施工进度计划及保证措施”* 时，检索条件硬性注入：
  `WHERE section_title IN ('第三章 施工方案说明', '第一节 施工进度计划安排')`
- **效果**：检索空间由 300 页骤降至 5 页，清除 98% 无关干扰段落。

### 3.3 第三层：评分项 Query 同义扩充 (Query Rewriting & Expansion)
- **原理**：使用 LLM 在检索前自动将评分标准扩充为 3~4 个招投标同义表达词。
- **示例**：`“应急故障处理响应时间”` ➔ 扩充为 `[“应急故障处理”, “售后服务响应”, “2小时到达现场”, “故障报修及维保”]`。

### 3.4 第四层：向量 (Dense) + 关键字 (Sparse) 混合检索与 RRF 融合
- **Dense Vector Search**：捕捉长段落语义相似度。
- **Sparse Key-phrase Matching (BM25/ILIKE)**：锁定型号、数字、专有名词。
- **RRF (Reciprocal Rank Fusion) 算法**：融合排名，取 Top 3~5 最佳切片。

### 3.5 第五层：父子切片与上下文还原 (Parent-Child Chunk Expansion)
- 当向量命中精细的子切片 (Child Chunk) 后，系统自动向前后扩展 1~2 个切片，或自动调出 Parent 完整大章，确保送给评分 Agent 的上下文具备完整的逻辑语境。

## 4. 三层金字塔层次化自适应分块架构 (3-Tier Hierarchical Chunking)

针对 Markdown 文本构建结构化的切片金字塔：

```
                              ┌────────────────────────────────────────┐
                              │  L1: 顶级大章块 (Parent Major Chapter) │ 
                              │  (例如: 《九、投标人情况介绍》, ~10k字)│
                              └──────────────────┬─────────────────────┘
                                                 │ 父子关联 (parent_chapter)
                              ┌──────────────────▼─────────────────────┐
                              │  L2: 语义检索切片 (Semantic Chunk)    │ 
                              │  (例如: 《业绩一览表段落》, 800~1200字)│
                              └──────────────────┬─────────────────────┘
                                                 │ 复制表头 (Header Continuation)
                              ┌──────────────────▼─────────────────────┐
                              │  L3: 表格原子保护块 (Atomic Table)     │ 
                              │  (例如: 完整 Markdown 独立表格)        │
                              └────────────────────────────────────────┘
```

### 4.1 L1 层：顶级大章块（大局保护与要素提取层）
- **划分规则**：依靠 `_extract_toc_chapters` 提取的目录白名单确定大章。
- **核心作用**：供要素提取 Agent 进行整章实体抽离；为下方 L2/L3 切片提供父级锚点。

### 4.2 L2 层：语义自适应切片（向量检索主载体层）
- **目标长度**：`800 ~ 1,200` 字符，带有 `150` 字符重叠 (Overlap)。
- **切分规则**：按 `##` 或句号 `。` 优雅自然拆分，绝不在句中断开。

### 4.3 L3 层：表格原子保护块（核心表单保护层）
- **绝不拦腰截断**：字数 `< 1,200` 的表格完整保存为一个独立 Chunk。
- **超大表格“带表头拆分” (Header Continuation)**：长表格按行切分时，每个子切片顶部强制粘贴原表格的表头 (`| 序号 | 项目名称 | 金额 |`)，确保上下文不丢失。

## 5. 切片元数据规范 (Chunk Metadata Schema)

每个落库的 `DocChunk` 具备如下元数据结构：

```json
{
  "chunk_id": "chunk_00122",
  "document_id": "doc_a47b6872",
  "chunk_level": "L2",
  "parent_chapter": "九、投标人情况介绍",
  "section_title": "2023年以来类似项目业绩一览表",
  "content_type": "table",
  "has_table": true,
  "page_start": 129,
  "page_end": 130
}
```
