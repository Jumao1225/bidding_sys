# 改动记录 (Changelog) - 2026-07-28

## 1. 移除文件缓存机制，改为 trigger→download 流水线复用

### 问题
- 前端先调 `POST /.../trigger` 触发填报，再调 `GET .../download` 下载结果
- 原来 `download` 端点在 `outputs/` 目录有旧文件缓存，命中后直接返回，不跑流水线
- 用户要求不使用文件缓存，每次保证最新结果

### 改动
- **[MODIFY] `app/api/endpoints/bid_generator.py` — `download_human_filled_bid_format`**:
  - 移除 `outputs/human_fill_results/` 缓存命中分支
  - 新增优先读取 `uploads/drafts/human_fill_result_{doc_id}.docx`（trigger 端点持久化的结果）
  - 兜底路径改为调用方案 C（BidFillerAgent），结果也存入同一持久化目录
- **[MODIFY] `app/api/endpoints/bid_generator.py` — `download_agent_filled_bid_format`**:
  - 同上，移除 `outputs/agent_fill_results/` 缓存命中分支
  - 新增优先读取 `uploads/drafts/agent_fill_result_{doc_id}.docx`
- **[MODIFY] `app/api/endpoints/bid_generator.py` — `trigger_human_like_bid_filling`**:
  - 移除旧的 `outputs/human_fill_results/` 缓存清理逻辑
  - 结果保存从临时目录改为 `uploads/drafts/` 持久化目录
- **[MODIFY] `app/api/endpoints/bid_generator.py` — `trigger_agent_bid_filling`**:
  - 移除 `outputs/agent_fill_results/` 缓存写入
  - 新增结果保存至 `uploads/drafts/agent_fill_result_{doc_id}.docx`

## 2. /human-fill-bid-format 内部委托给方案 C

### 问题
- `/human-fill-bid-format/` 端点内部仍调用已废弃的方案 B（HumanLikeBidFillerAgent）
- 方案 B 只是逐槽位查库 + 直接粘贴原始值，没有"阅读文档 → 理解语境 → 专家撰写"环节
- 用户实际使用的是方案 B，而非增强后的方案 C

### 改动
- **[MODIFY] `app/api/endpoints/bid_generator.py` — `trigger_human_like_bid_filling`**:
  - 删除 `bid_format_filler_service.fill_bid_document_human_like()` 调用（方案 B）
  - 改为直接调用 `bid_filler_agent.process_filling_tasks()`（方案 C）
  - 结果保存至 `uploads/drafts/human_fill_result_{doc_id}.docx`
- **[MODIFY] `app/api/endpoints/bid_generator.py` — `download_human_filled_bid_format` 兜底路径**:
  - 删除 `fill_bid_document_human_like()` 调用
  - 改为调用 `bid_filler_agent.process_filling_tasks()`（方案 C）

## 3. 修复 Agent 同步/异步工具不兼容（StructuredTool does not support sync invocation）

### 问题
- `agent_fill_node` 使用 `agent.invoke()`（同步），但三个 OfficeCLI MCP 工具包装内部调用了异步方法
- DB 工具（`bid_db_tools.py`）是同步 `@tool`，正常工作
- MCP 工具调用异步 `office_cli_mcp_client` 方法时，LangChain 报错 `StructuredTool does not support sync invocation`
- 导致 Agent 两次重试全部失败，流水线未能实际写入 Word

### 改动
- **[MODIFY] `app/agents/bid_filler_agent.py` — `agent_fill_node` MCP 工具包装**:
  - 新增 `_sync_call_async(coro)` 辅助函数，安全地在同步上下文中运行异步协程：
    - 无事件循环 → `asyncio.run()`
    - 有事件循环（FastAPI 上下文）→ `ThreadPoolExecutor` 新线程独立事件循环
  - 三个 MCP 工具（`officecli_query_doc_structure` / `officecli_batch_update` / `officecli_add_table_row`）全部改为通过 `_sync_call_async()` 调用 `office_cli_mcp_client` 异步方法
  - 移除对旧 `mcp_officecli_*` LangChain tool 的 `.invoke()` 包装依赖

## 4. Prompt 强化：禁止照搬数据库原始值 + 抽象占位符防幻觉

### 问题
- Agent 可能将数据库返回的原始数据直接填入 Word，不做标书语言转化
- System Prompt 中含有真实业务数据（公司名、人名、金额等），违反防幻觉规则

### 改动
- **[MODIFY] `app/agents/bid_filler_agent.py` — System Prompt**:
  - 新增"核心工作流" 4 步：阅读 → 查库 → 🧠专家撰写 → 写盘
  - 新增"🚨 最高指令"：你不是数据搬运工，每个字段必须经标书语言转化
  - 新增"标书专家撰写规则"：9 种场景的 ❌/✅ 对照范例（公司名、人名、金额、日期、工期、质量、地址、保证金、空表格）
  - 所有真实数据替换为抽象占位符（`XXX有限公司`、`XXX（姓名）`、`XXXXXX.XX` 等）
  - 拆分 Prompt 为 `SystemMessage`（静态）+ `HumanMessage`（动态），利用 LLM prompt caching
- **[MODIFY] `app/agents/bid_filler_agent.py` — `scan_node`**:
  - 新增 LLM Slot Analyzer 预识别（`analyze_slots_with_llm`），一次性感知文档空白槽位
  - 结果通过 `_build_slot_hint()` 注入 Agent Prompt，减少 Agent 探索 Token 消耗
- **[MODIFY] `app/agents/bid_filler_agent.py` — `agent_fill_node` 工具集**:
  - 新增 `analyze_word_table` @tool（集成 TableAgent 零硬编码表格列语义映射）
  - Agent 总工具数：6 DB + 3 MCP + 1 TableAgent = 10

## 5. 方案 C 系统收敛总结

### 已完成的架构变更
| 组件 | 之前 | 之后 |
|------|------|------|
| 金额大写 | 3 套重复实现 | 统一 `rmb_formatter.py` |
| DB 工具 | 方案 C 内联重复包装 | 直接复用 `bid_db_tools.py` |
| Orchestrator writer_agent | 方案 A（WriterSupervisor） | 方案 C（BidFillerAgent） |
| `/human-fill-*` API | 方案 B（HumanLike） | 委托方案 C |
| 废弃文件 | — | 7 个文件标记 @deprecated |
| 槽位识别 | Agent 自主探索（Token 浪费） | SlotAnalyzer 预识别注入 |
| 表格填充 | 无智能分析 | TableAgent 零硬编码映射 |
| MCP 工具 | 异步不兼容 | `_sync_call_async` 兼容层 |
| 执行可靠性 | 无超时/重试 | 可配置超时 + 2 次重试 + sandbox 快照恢复 |
