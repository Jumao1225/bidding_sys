# 变更日志 - 2026-08-26

## 核心更新

### 6. 修复投标文件格式 LLM 提取的租户 ID 未定义
- **问题背景**：下载 PDF 招标文件的“投标文件格式”模板时，服务记录 `NameError: effective_tenant_id is not defined`，LLM 提取流程被错误降级为基础模板。
- **问题根因**：`extract_and_export_bid_format` 已计算有效租户 ID，但调用 `_extract_with_llm_and_rebuild` 时未传递；私有方法内部却直接引用了未定义的局部变量。
- **核心改动**：为 `_extract_with_llm_and_rebuild` 增加可选 `tenant_id` 参数，优先使用调用方显式传入值并兼容回退至文档所属租户；入口将已解析的有效租户 ID 显式传递给 LLM 提取流程。
- **测试验证**：扩展 `test_bid_format_extractor.py`，断言 LLM 配置检查及结构化生成均接收文档所属租户 ID，并保留异常降级路径验证。
- **影响范围**：PDF 或原生 Word 切片失败时的投标文件格式提取，以及后台线程调用下的租户级模型配置选择。
- **涉及文件**：
  - `backend/app/services/bid_format_extractor_service.py`
  - `backend/tests/unit/test_bid_format_extractor.py`

### 1. 修复工程设备清单提取静默返回 0 项
- **问题背景**：工程清单分块调用 LLM 成功但最终汇总为 0 项，空结果仍可能覆盖数据库中的有效工程元数据。
- **问题根因**：结构化 Schema 默认忽略未知字段并使用空数组默认值；分块异常缺少堆栈日志；汇总阶段未拦截“检测到表格但没有设备明细”的异常结果。
- **核心改动**：
  - 修正工程提取工具读取文档时错误调用需要权限参数的 CRUD 方法，恢复完整 `output.md` / 全量 Chunk 提取路径，避免异常后降级到全局 RAG。
  - `EquipmentItem`、`TechValidationRequirement`、`EngineeringSchema` 启用严格字段校验，阻止错误字段名被静默忽略。
  - 为每个分块记录设备数量、示例名称和输入长度，并使用 `logger.exception` 记录完整异常堆栈。
  - 检测到工程表格但汇总设备明细为 0 时抛出异常，拒绝执行空结果落库。
  - 单表短文本路径改为先完成空结果校验，再执行元数据落库。
- **测试验证**：新增空结果拦截和未知字段校验单元测试；同步调整租户传递测试使用有效设备项。
- **涉及文件**：
  - `backend/app/services/metadata/engineering_service.py`
  - `backend/tests/unit/test_engineering_service.py`

### 3. 限定 BOM 提取上下文仅来自可计价 BOQ 清单
- **问题背景**：放开施工/服务类 BOQ 后，安全管理、岗位职责、作业票和违章分类等非计价内容也被作为 BOM 项目提取，导致清单数量异常膨胀。
- **问题根因**：表格预处理仅按宽泛关键词识别设备/工程表格，并将最后一个表格后的整段正文追加到模型上下文；Prompt 也允许仅凭“工作内容/服务描述”生成清单项。
- **核心改动**：
  - `extract_equipment_tables_and_context` 改为要求表格同时具备名称类字段与数量/单位/计价类字段，或具备明确的工程量/采购/报价清单上下文。
  - 增加安全生产、文明施工、违章库、岗位职责、风险管理、管理制度、培训、评标等非 BOQ 上下文排除规则。
  - 删除最后一个表格后的全文追加逻辑，仅向工程提取模型传递 BOQ 表格及其邻近标题。
  - Prompt 增加“数量/工程量 + 单位/计价依据”门槛，明确排除安全制度、施工方法、风险提示和一般合规条款。
- **测试验证**：`python -m pytest -q backend/tests/unit/test_equipment_table_filter.py backend/tests/unit/test_engineering_service.py`，6 passed。
- **涉及文件**：
  - `backend/app/utils/table_utils.py`

  - `backend/tests/unit/test_equipment_table_filter.py`
  - `backend/tests/unit/test_engineering_service.py`

### 2. 扩展工程清单提取范围以覆盖施工与服务类 BOQ 项目
- **问题背景**：工程量清单中的“电缆直埋”“交通工程”等单位为“项”的施工/服务行项目未被提取，仅保留了“灭火器箱”等实体设备材料。
- **问题根因**：工程提取 Prompt 将目标限定为核心设备、材料、元器件和成套总成，并要求过滤现场操作工序，模型据此排除了有效的施工与服务类清单行。
- **核心改动**：
  - 将提取目标扩展为完整 BOM/BOQ，要求逐行保留设备、材料、安装、施工、运输、调试、检测和其他服务项目。
  - 明确规定不得因单位为“项”“批”“次”“日”“人月”，或名称属于施工工序/服务项目而过滤有效行。
  - 要求保留父级分部项目及子项目，使用 `item_code`、`parent_item`、`root_item` 和 `tree_level` 表达层级。
  - 将 `quantity` 字段语义扩展为设备材料的采购数量，以及施工/服务项目的原文工程量或服务次数。
  - 增加回归测试，验证 Prompt 会将“电缆直埋”“交通工程”等施工类 BOQ 行纳入提取上下文和输出约束。
- **测试验证**：`python -m pytest -q backend/tests/unit/test_engineering_service.py`，4 passed。
- **涉及文件**：

### 4. 修复成本分析保存 422 与结构化参数导致的 React 崩溃
- **问题背景**：成本分析页面保存 BOM 明细时返回 `PUT /api/v1/analysis/{document_id}/cost-analysis` 422，同时浏览器提示不能直接渲染包含 `{type, input}` 的对象。
- **问题根因**：历史解析数据中的结构化关键参数被前端直接渲染并原样提交，而后端请求模型要求 `key_parameters` 为 `List[str]`；另外前端可能将空单位提交为 `null`，与原有非空字符串约束不一致。
- **核心改动**：
  - 前端新增成本字段归一化函数，将 `{type,input}` 等结构化值转换为文本，统一清洗关键参数数组、区域、品牌、备注及成本总结，并在提交时保证关键字段为字符串。
  - 成本保存请求为空单位补充默认值“项”，避免历史空单位触发请求校验失败。
  - 后端兼容旧结构化文本字段，将关键参数统一转换为字符串列表，并允许单位显式为空。
- **测试验证**：`python -m pytest -q backend/tests/api/test_cost_analysis_update_api.py`，6 passed；前端 `CostTable.tsx` 未产生新增 TypeScript 错误，但组件测试受仓库既有 Ant Design ESM/CJS 依赖冲突阻断，未进入用例执行。
- **影响范围**：成本分析 BOM 表格的历史数据展示、手动保存及关键参数持久化。
- **涉及文件**：
  - `frontend/src/components/CostTable.tsx`
  - `frontend/src/components/CostTable.test.tsx`
  - `backend/app/api/endpoints/analysis.py`
  - `backend/tests/api/test_cost_analysis_update_api.py`

### 4. 修复工程量清单跨页续表被过滤
- **问题背景**：实际标书重新提取后仅得到 6 项，日志显示前两个分块均未提取到设备明细，只有首张工程量清单表返回结果。
- **问题根因**：工程量清单跨页拆分为多张 HTML 表格，后续表格没有重复表头；表格筛选器只按表头判断，且续表首行的施工描述包含“施工规范”，被误判为非 BOQ 内容后提前终止清单上下文。
- **核心改动**：
  - 增加活动 BOQ 上下文状态，无重复表头的相邻续表自动继承上一张工程量清单的筛选结果。
  - 仅在尚未进入 BOQ 上下文时检查表头中的非清单关键词，避免把续表数据描述误判为安全/规范表头。
  - 遇到设备材料品牌表、工程结算单、安全文明施工违章库和常规施工风险等明确后续章节时终止续表继承。
- **测试验证**：相关单元测试 `7 passed`；针对实际标书 `output.md` 验证保留 3 张 BOQ 表、包含光伏组件/箱式变压器/垂直接地极等续表项目，并排除品牌供应商表、安全违章表和结算表。

### 5. 修复工程量清单分组编号误判为 BOM 子项
- **问题背景**：`2.6.1`、`2.6.2`、`2.6.3` 等同级工程量清单行被模型串成多级 BOM，前端显示为 L3、L4、L5、L6，并产生错误的成套汇总。
- **问题根因**：Prompt 将编号点号层级作为 BOM 层级依据，同时允许无数量、无单位的“接地”“预埋管”等分组标题作为父节点；模型又可能把相邻同级行继续挂载成父子链。
- **核心改动**：
  - Prompt 明确区分工程量清单编号与真实 BOM 层级，规定仅凭点号编号、相邻顺序或名称相似不得建立父子关系。
  - 无数量、无单位的分组标题不再输出为 `EquipmentItem`，也不能作为 `parent_item`。
  - 新增 `_normalize_boq_hierarchy` 确定性校验：按原始编号校验直接父项，移除非计价分组行，并将 `2.6.1～2.6.6` 这类同级计价行归一为 `tree_level=1`。
- **测试验证**：工程服务与表格筛选测试 `8 passed`；多级 BOM 兼容测试 `8 passed`；对当前数据库数据验证 `2.6` 分组标题被移除、`2.6.1～2.6.6` 均恢复为独立一级行。
- **涉及文件**：
  - `backend/app/services/metadata/engineering_service.py`
  - `backend/tests/unit/test_engineering_service.py`

### 8. 隔离标书撰写进程并限制并发提交
- **问题背景**：点击“撰写标书”后，Word 解析、Agent 推理和多章节并发写盘仍运行在 FastAPI 所在进程，导致同一服务中的页面数据请求和普通接口出现卡顿或长时间无响应。
- **问题根因**：`POST /api/v1/bidding/agent-fill-bid-format/{document_id}` 使用守护线程执行长流程；线程与 Web 进程共享 CPU、Python GIL 和数据库连接，且没有同文档互斥或全局并发上限。
- **核心改动**：
  - 将标书撰写改为 Windows 兼容的 `spawn` 独立子进程，API 仅负责提交并立即返回进程标识；当前不依赖 Celery Worker。
  - 新增 Redis 文档锁与全局槽位锁，默认最多并行执行 1 份标书；重复提交同一文档或槽位已满时返回 409，避免 Word 临时文件和审计日志竞争。
  - 子进程在任务结束后通过 Lua 比较并删除锁，避免锁过期重分配后误删其他任务的锁；Redis 不可用时接口返回 503，防止无保护地继续启动重任务。
  - 增加 `BID_FILL_MAX_CONCURRENCY` 与 `BID_FILL_LOCK_TTL_SECONDS` 配置项，默认分别为 1 和 14400 秒。
- **测试验证**：`python -m pytest -q backend/tests/unit/test_bid_fill_task_service.py backend/tests/api/test_bid_generator_api.py`，15 passed。
- **影响范围**：Agent 全自主标书撰写入口、Redis 任务保护和前端撰写请求的任务标识返回；不影响既有 SSE 日志订阅方式。
- **涉及文件**：
  - `backend/app/api/endpoints/bid_generator.py`
  - `backend/app/services/bid_fill_task_service.py`
  - `backend/app/core/config.py`
  - `backend/tests/unit/test_bid_fill_task_service.py`
  - `backend/tests/api/test_bid_generator_api.py`
