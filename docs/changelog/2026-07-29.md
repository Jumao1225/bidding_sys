# 改动记录 (Changelog) - 2026-07-29

## 1. 修复 BidFillerAgent 工作副本临时路径越界导致下载接口二次全量触发的问题

### 问题
- `app/agents/bid_filler_agent.py` 中的 `scan_node` 及 orchestrator 节点中，使用 `os.path.dirname(__file__)` 往上溯源计算项目后台基本路径时使用了 4 次，导致跳出了 `backend` 本身而跨越到了主系统根目录（`D:\Myproject\bidding_sys\uploads\drafts`）。
- 导致 `app/api/endpoints/bid_generator.py` 中通过 `os.getcwd()` 计算并找寻的 `backend/uploads/drafts/` 结果无法与其实对齐。
- 前端向后继发送 `GET /.../download` 请求时，接口寻找 `human_fill_result_{doc_id}.docx` 缓冲未果，误判定计算流程异常并当头二次引战启动大模型的计算全流水线（长约 17.3s）。
- 同时由于当地网络或连接端口不可用（未连同中继口导致 /chat/completions 一贯回退报错 `Connection error`），从而出现 0 提案重发崩溃返回的表象。

### 改动
- **[MODIFY] `app/agents/bid_filler_agent.py`**:
  - `scan_node`: 修改对 `__file__` 往上的父目录解算深层往推个数：将原有连续 4 层的 `os.path.dirname` 下缩为精准的 3 层。确保挂归向对齐为 `backend/uploads/drafts`。
  - `bid_filler_orchestrator_node`: 将落盘时计算 `base_dir` 的相同超层越级 Bug (4次 dirname 缩减为 3次) 一并实施完全对齐收缩修复。

- **[MODIFY] `tests/unit/test_bid_filler.py`**:
  - 遵循测试驱动理念，新增针对 `scan_node` 临时路径生成的回归用例验证函数 `test_scan_node_temp_path_should_be_in_backend_dir`，从底层验证生成的缓存临时表路径绝对在系统的 `backend` 分割线内存续运转，已通过所有单元功能实测验证 (`pytest tests/unit/test_bid_filler.py -v`)。

## 2. 彻底解决《开标一览表》等章节前台显示已填好，但导出的 Word 文档实际完全留白的问题

### 问题
- 原来的流程中，把多达上百行的 `worker_proposals` 作为长参数丢给 Review Agent，命强大模型写一段长达几千字符的 JSON `[{"command":"set","path":...}]` 调用 API 写磁盘。在生成这类有规律的明细大表单时，大模型因为 tokens 和注意力惯性常常截断打折，直接偷工减料忽略掉了后面的开标清单不写。
- 当 Worker 定位到的表格单元格路径直接以 `/tc[N]` 结束时，向该单元格写盘易抛出 `Path not found`，底层的 `apply_batch` 为避免影响整体程序会采取“静默式剔除”不报错，导致明明算清写回的开标一览最终没有写进物理文档。
- 此外，原有基础筛查把所有 `source_tool == 'none'` 或未附具查询原名称的的提案强判定为无效，直接砍掉流弃。不少经过换算（如自主汇总算出的人民币金额和表格文字）往往会被这一刀切错杀过滤。

### 改动
- **[MODIFY] `app/agents/bid_filler_agent.py`**:
  - 剥离对 Reviewer 大模型手动拼装大规模写盘 JSON 数组的过度依赖。现在由 Python 代码统一同步且一锤不漏地执行底层安全写盘 (`_fallback_write_commands`)，大模型降容解压仅担当单纯质检复核工作。
  - 放款并改善 `proposals_to_commands` 初筛规则：完全去除了对待写提案里 `source_tool == 'none'` 或空白时的红杠硬锁判定；为所有直指表格尾端 (`/tc[\d+]`) 的 XPath 智能吸附挂搭为其单元内原生头层级文字节点 (`/p[1]`)，断绝表格写入因路径定界出入发生的丢错抛开异常。
- **[MODIFY] `tests/unit/test_bid_filler.py`**:
  - 为上述修复机制全新设计提交了极简高效的 `test_proposals_to_commands_should_handle_none_source_and_wrap_tc` 用例回归验证，成功覆盖上述多类型场景并百分百平顺贯通过测。

## 3. 彻底解除原系统对待填表项与文本段落下 `@paraId` XPath 的一刀切错杀过滤（打通完整章节填入最后屏障）

### 问题
- 真实系统全链路测试和审计跟踪发现：每次执行至最后审查过滤池时，固定会有达 46 条已填好（占比约 27%）的有效提案被系统作为废弃垃圾拦截扔弃。受殃最大的重灾区为 **《技术要求响应及偏离表》** 和 **《资格证明文件》**，因遭全盘误杀导致这几个整块重要文档最终输出为完全留白。
- 根因定位到：当且仅当 Worker 大模型使用 `OfficeCLI query` 原生查询段落文档结构并选准具体位置时，底层原生的格式表达就是 `/body/p[@paraId=...]`；但老项目写死的初筛校验判定语句中却荒谬地将 `if "@paraId" in path` 设置为了直接一刀切触发 `reject`（并在大模型 Prompt 中重名列令勿沾染）。
- 经深入底层的真实快照实盘压测确认：`OfficeCLI` 的主批量写盘接口本身百分之百完全并且原生直接支持针对 `@paraId` 的物理地址锚定直译打实！该一刀切逻辑属于重度认知误解所引致的设计后门的典型破坏事故。

### 改动
- **[MODIFY] `app/agents/bid_filler_agent.py` & `app/agents/bid_filler_workers.py`**:
  - **断然移除旧制卡脖子陷阱**：直接移除了 `proposals_to_commands` 等全部过滤分流关卡里对待查验或准接入路径的 `@paraId` 一致杜绝断定。
  - **规导大模型放心施为**：优化修正 Worker 的底板生成话术与示例指引规范，告言模型尽可理直气壮畅行选用包括 `@paraId` 及原生常规正整数序号双链写直表单位置。
- **[MODIFY] `tests/unit/test_bid_filler.py`**:
  - 加挂针对 `@paraId` 特征长链向底层稳投渗透放开的集成化和精简阻挡考核条目，实证了不再错失阻挂任何一个常规段落打桩意愿。

## 4. 彻底解决《投标配置及分项报价表》中逆变器及并网柜等关键设备缺失单价和总价（合价）的问题

### 问题
- 实际投流结果中用户发现：《投标配置及分项报价表》上逆变器与并网柜两类主设备数量、单价与合计价出现了缺单与待补充填空，未完全顺从底层数据回写。
- **原因剖析**：
  1. 数据库内 `CostEstimate` (成本估算及 BOM 详细表) 明明真实存储着全量且精确的标的设备台账（如逆变器6台11555元/台、并网柜2台9180.35元/台以及分别的合价总金额）。
  2. 但底层的财务与报价查库工具函数 `query_financial_quotation_tool` 内部，只有匹配“大写/总价/保证金”这少数几个关键词的分流语句；一旦大模型想要索讨整张 BOM 表（如传递 `cost_estimates`、`分项报价`、`清单` 等查询时），接口永远被简单粗暴地强制 fallback，单一回喷 `967840.36` 这数字型全局综揽合计总金额。造成智能体彻底丧失感知底层分项合价和设备件数的视域！
  3. Guidance 参考单价接口 `query_market_price_reference_tool` 原始查询仅仅死守对单一名字字段的完整强模糊硬碰死等（如传递组合搜索 `组串式逆变器 华为 110kW` 时就会搜个全空），也绝不会向已经算定好总价和工程件数的 BOM 台表跨步借取全套造价说明。

### 改动
- **[MODIFY] `app/agents/tools/bid_db_tools.py`**:
  - **直接解封分项大满贯拉取力**：为 `query_financial_quotation_tool` 原生开拓装入了直接响应打拔如 `"cost_estimates" / "bom" / "分项" / "清单"` 关键字指引的提取快车道，直接把当前文件下各条核心及周边产品的规格型号、台件用量、核定参考单价与决议合并价汇总梳理出表回馈！
  - **构建复合词切片与合价渗透借览搜索**：大幅改造升级 `query_market_price_reference_tool`，一旦精准搜寻挂零就启动对复合关键字（带有型号与厂牌名称的复合词汇）的长短分字切干递进排查；并同时无缝桥接且直探向当前项目的工程实际计费 BOM (CostEstimate) 实有台账池，把品目下单品单价、预备消耗量和已定夺的总价一同打进大模型分析视眼。
- **[MODIFY] `app/agents/bid_filler_workers.py`**:
  - 为专管表格的数据类打工者 (`needs_data` Worker) 原生添加战法要义与实战指导建议：叮嘱凡逢主配明细与造价单，直接挑牌传值打桩执行上述两大新启装机武器工具口，一击尽得数量与造价。

  - 在 `bid_db_tools.py` 的 API 说明里，带有明确的“逆变器、并网柜、华为”等光伏专有设备名词及样本参数；

  - 不具备平台灵活性与泛化弹性：当切换至医疗建筑或路桥勘建施工时，此类死样本和专有名字会阻断思考判断。

### 改动

  - **清洗重修 API Docstring 与指引言**：把所存关于特定领域的具体物料与标底合单品牌名称完全撤除，悉数代换改造为 `"某品类主设备" / "XXX核心主机" / "XXX技术规范" / "某配套总成"` 等标准中性化抽象表示法。

## 7. 实施大模型强稳零调测速仪与精干切口防散注聚光视网口构建（最大程度确立稳定性与精炼率）

### 问题
- **模型采样抖动隐患**：即使采用了无数字幻觉预设及清洁型系统引导，如果在主工作组（Supervisor、Reviewer、各表单 Worker）上共用原本 default=0.3 的模型随机概率下发抽样层，长周期的表格回抄与精准金额换位不可避免产生由高温导致的推演用词抖动。
- **注意力稀释**：在老实现逻辑中，当专门钻查某一小表件（比如仅仅看“消耗性备品配单”）的工兵去调用 `officecli_query_structure(selector="table")` 问需时，直接把数百上千行混装别的全部章节大表的 XML 都拉下来混成了一股全量杂文塞入了该局部小组眼口，导致严重的 Prompt Attention Leaks。

### 核心改进与实现
- **[MODIFY] `app/agents/bid_filler_workers.py`**:
  - **切碎视口防散精算器 `_filter_dom_scope` 新入驻**：打造专属算法核心层；每位工兵可通过原生带参结构搜索中自报的 `keyword_filter="目的专指或当前目标大名"` 直拉触法！系统只取完全符合关键字点位并延四周反延最大 $\pm 3$ 段纯干货局部视距段！瞬间洗却跨小群及多份表格交错下杂合污染。
  - **客观属性死顶层温度常零锁死 (Zero-Temperature Engine Binding)**：根据工序任务性征辨异，若断记为 `needs_fill` (传统字段空格) 或 `needs_data` (表格核算数据填提)，即强制派办只发恒为 **`temperature=0.0`** 的高精确定型单线模版；无论几路跑多少遭，回函全均一式不走调。
- **[MODIFY] `app/agents/bid_filler_agent.py`**:
  - **全总揽大员一并看齐零偏**：重整切对上层的决策大帅 `supervisor_agent` 和守御终局关卡的审议官 `reviewer` 双方皆换搭由 `llm_service.get_llm(temperature=0.0)` 直接灌顶供应出的零变异恒久判断内核。实现上下主路同力如规一致不变。
