### 1. 修复重新分析接口加锁冲突时误释放未持有锁引发 LockError 异常

- **问题背景**：当用户在前端短时间内多次触发履约盘点（`strategy_qual`）或风险提示（`strategy_risk`）重新提取接口，或者上一轮分析任务仍在执行时，接口返回 409 状态码，并在后台错误日志中打印 `redis.exceptions.LockError: Cannot release a lock that's not owned or is already unlocked.` 及冗长的异常调用栈。
- **问题根因**：
  - 在 `backend/app/api/endpoints/analysis.py` 的 `reextract_domain` 接口中，`analysis_lock` 在调用 `redis_client.lock(...)` 后被赋值为锁实例对象。
  - 当非阻塞加锁 `analysis_lock.acquire(blocking=False)` 失败抛出 `HTTPException(409)` 时，函数进入 `finally` 代码块。
  - `finally` 中仅简单判断 `if analysis_lock is not None:` 便直接调用 `analysis_lock.release()`。由于当前请求并未成功获取该锁，`redis-py` 抛出 `LockError`，导致正常的并发拦截逻辑附带了严重的异常堆栈日志输出。
- **核心改动**：
  - **后端修改**：
    - 在 `backend/app/api/endpoints/analysis.py` 的 `reextract_domain` 中新增 `lock_acquired = False` 状态标志。
    - 仅在 `analysis_lock.acquire(blocking=False)` 成功返回 `True` 时将 `lock_acquired` 置为 `True`。
    - 在 `finally` 块中将释放条件更新为 `if analysis_lock is not None and lock_acquired:`，确保未成功持有锁的请求不会触发 `release()`。
  - **测试验证**：
    - 在 `backend/tests/api/test_reextract_api.py` 中新增 `test_reextract_strategy_qual_conflict_should_return_409_and_not_release_unacquired_lock`，模拟加锁冲突返回 409 并断言 `fake_lock.release` 未被调用。
    - 新增 `test_reextract_strategy_qual_success_should_acquire_and_release_lock`，断言正常执行成功后会正确释放锁。
    - 执行 `pytest tests/api/test_reextract_api.py -v`，全部 7 项测试均通过（7 passed）。
- **影响范围**：
  - `POST /api/v1/analysis/{document_id}/reextract/{domain}` 接口中涉及分布式锁的专项分析（如 `strategy_qual`、`strategy_risk`）。

### 6. 修复多级 BOM 成套统价锁定冲突、展示不一致与总额双重计费缺陷

- **问题背景**：
  - 在多级嵌套 BOM 场景（如 L1 成套主标的 -> L2 成套总成 -> L3 设备部件）中，当母项 L1 设定了自定义成套统价（如 10.00 元）后，下级已被上级锁定的中间成套项 L2 虽标注了 `[🔒 父项统价锁定]` 徽章，但界面仍显示独立参考单价 7500.00 元和小计 7500.00 元（父项统定价总计），右侧操作栏仍显示可编辑按钮；
  - 导出 Word/Excel 时，部分情况下总价出现 10 + 7500 = 7510 元的双重计费，且导出的明细表中被锁定的子构件仍残留独立价格；
  - 前端渲染时因缺少 `isManualEdit` 变量声明导致 TypeScript 提示 `Cannot find name 'isManualEdit'`。
- **问题根因**：
  - **前端判断短路**：`CostTable.tsx` 中的 `isParentCustom` 判定为 `record.isParent && (record.is_parent_modified || record.pricing_mode === 'parent')`。中间节点 L2 曾设置过统价，自身同时满足 `isParent` 和 `pricing_mode === 'parent'`；且在单价、小计、匹配信息单元格渲染中，`isParentCustom` 分支排在 `isLockedByParent` 之前，导致即使被母项锁定，中间节点依旧走了母项统价的分支展示；
  - **后端累加漏洞**：`bom_export_service.py` 的 `_calculate_export_total` 在累加时，只排除了“普通父项”，而对所有 `is_parent_custom` 节点进行了小计累加，导致 L1 的 10 元与 L2 的 7500 元均被计入总额；
  - **变量未定义**：在 `CostTable.tsx` 的设备名称列与置信度列中，模板使用了 `(isManual || isManualEdit)`，但列内部只定义了 `isManual`（手动添加），未声明 `isManualEdit`（手动修改）。
- **核心改动**：
  - **前端 CostTable 组件**：
    - 将 `isParentCustom` 的定义严格约束为 `record.isParent && (record.is_parent_modified || record.pricing_mode === 'parent') && !record.isLockedByParent`，确立成套统价的“祖先支配权（Parent Dominance）”原则；
    - 在名称列、匹配信息列与置信度列中补齐 `const isManualEdit = record.match_quality === '手动修改'`，彻底消除 `Cannot find name 'isManualEdit'` 的编译与运行时引用异常；
    - 提升 `isLockedByParent` 的分支优先级，对于被锁定的中间成套项与底层子项，单价规范展示为 `-- 已统入父项价`，小计展示为 `--`，匹配信息展示为专用“🔒 统价锁定说明：已统入上级成套价”卡片；
    - 在 `rollupNodePrices` 汇总中加入 `isLockedByParent` 拦截，被锁定节点内部 `subtotal` 归零，杜绝脏累加；
    - 操作栏对被锁定的中间父项彻底禁用 ✏️ 编辑按钮与 `+` 添加子项按钮，隐藏“重置父项”按钮，防止在锁定状态下引发状态混乱。
  - **后端层级汇总服务 (`cost_service.py`)**：
    - 在 `rollup_hierarchical_cost_items` 中增加自顶向下递归传递的 `_apply_parent_lock`，当祖先启用成套统价后，所有后代节点自动标记 `is_locked_by_parent = True` 且其内部独立小计归零；
    - 规范未匹配项统计，被成套统价锁定的子项不再计入 `unmatched_count`。
  - **后端导出服务 (`bom_export_service.py`)**：

### 7. 实现多子项成套设备父子价格互斥定价与清空解锁机制

- **问题背景**：
  - 用户在成套设备「光伏组件」上点击重置按钮后，界面数据与价格没有任何变动，下级新增子项 `qcw` 依然处于原位，且由于 `hasModifiedChildren` 的恒真判定，成套设备的编辑按钮陷入永久禁用死锁；
  - 核心业务诉求为**父子价格互斥修改**：成套父项有多个子项时，若父项处于统价模式，子项被锁定；父项提供按钮“清空父项价格并解锁下属所有子项”，点击后清空父项价格，名下全部子项解锁编辑；一旦下属任意子项录入了价格，成套价格必须完全由所有子项自动求和汇总得出，此时互斥锁定父项禁止直接修改；如需改回父项统价，需在父项点击“清空子项价格”以恢复未定价。
- **问题根因**：
  - 现有重置函数 `resetCostChildrenPreservingCustomItems` 仅针对有原始对标子项的成套设备设计，对下属全为手动新增项的场景保留了新增项且未清空父项独立价格；
  - `markMutualExclusion` 中将 `child.is_custom_added` 硬编码算为修改锁定，缺少 `hasPricedChildren`（子项是否具备有效金额）的精准判定；
  - 缺少真正的 `handleClearParentPrice`（清空父项自身价格，下放定价权给名下全部子项）与 `handleClearChildrenPrices`（清空名下全部子项价格，收回定价权给父项）。
- **核心改动**：
  - **接口扩充与互斥判定 (`CostTable.tsx`)**：
    - 在 `CostItemNode` 接口中增加 `hasPricedChildren?: boolean` 字段；
    - 重构 `markMutualExclusion`：遍历检查名下全部直接子项，统计 `anyChildHasPrice` 与 `anyChildModified`。当父项自身有统价且子项无价格时，父项统价主导并锁定下属全部子项；当子项中存在有效金额时，`isLockedByChildren = true`，自动互斥锁定父项直接修改。
  - **清空父项与清空子项双向解锁动作 (`CostTable.tsx`)**：
    - 新增 `handleClearParentPrice`：清空父项 `ref_price = 0, subtotal = 0, pricing_mode = 'children'`，并实时解除对名下全部子项的锁定，使下属所有子项立即获得独立定价权；
    - 新增 `handleClearChildrenPrices`：利用 `getCostResetChildIndices` 递归查找名下所有直接与间接后代子项，批量清零所有子项价格并设为未定价，使成套总价归零，重新解锁成套父项直接统价权限。
  - **操作栏按钮逻辑重构 (`CostTable.tsx`)**：
    - 成套父项 ✏️ 编辑按钮：当子项已有价格汇总时自动禁用，Tooltip 明确提示：“当前成套价格由名下全部 N 个子项汇总自动驱动，禁止直接修改父项。如需直接指定成套统价，请先点击「清空子项价格」”；当子项无价格时完全可用；
    - 成套父项操作栏新增 🔄【清空父项价格，解锁子项】按钮（`UndoOutlined`，在父项有价格且未被上级锁定时显示）；
    - 成套父项操作栏新增 🔄【清空子项价格，解锁父项】按钮（`ReloadOutlined`，在子项有价格时显示）；
    - 下属子项操作栏 ✏️ 编辑按钮：被父项统价锁定时禁用，Tooltip 精准引导：“所属成套设备已启用父项直接定价，下属所有子项已锁定。如需修改子项价格，请先在上方成套设备点击「清空父项价格」”。
