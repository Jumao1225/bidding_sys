## 智能 BOM 树形回溯挂载算法层级防同级兄弟项误吞并与匹配规则加固

### 1. 变更背景与问题定位
- **问题反馈**: 用户在智能 BOM 成本测算界面中发现，复合名称成套主项（如 `4(九) 铁附件、电缆防火封堵`，1级主项）下的平级子项（如 `#1 铁附件`、`#2 电缆防火涂料`、`#3 有机堵料`、`#4 无机堵料`、`#5 防火隔板`，均为2级元器件）出现层级错乱：
  1. `4(九) 铁附件、电缆防火封堵` 显示仅含 1 项；
  2. 兄弟项 `#1 铁附件` 被错误提升为 `2级成套总成 (含 4 项)`；
  3. 平级的 `#2 电缆防火涂料`、`#3 有机堵料` 等被错误降级为 `铁附件` 下属的 `3级元器件`。
- **根本原因**:
  - 前端 [`CostTable.tsx`](file:///d:/Myproject/bidding_sys/frontend/src/components/CostTable.tsx) 与后端 [`cost_service.py`](file:///d:/Myproject/bidding_sys/backend/app/services/cost_service.py) 在执行就近向上回溯挂载算法（Backward Scope Matching）时，名称判定规则包含了宽松的反向包含 `parentName.includes(prevName)` / `(prev_name in parent_name)`；
  - 当回溯遍历到 `#2 电缆防火涂料` 时，向上碰到的第一个兄弟项为 `prevName = "铁附件"`，由于 `"铁附件、电缆防火封堵".includes("铁附件")` 命中为 `true`，导致算法将兄弟项判定为了父节点并提前 `break` 终止回溯；
  - 同时回溯逻辑缺少 `prev.tree_level < node.tree_level` 的层级刚性校验。

### 2. 核心修复与升级
1. **移除反向子串宽松匹配**:
   - 彻底移除 `parentName.includes(prevName)` / `(prev_name in parent_name)` 匹配分支；
   - 仅允许精确匹配 `prevName === parentName` 或父节点全名包含子项指定父名 `prevName.includes(parentName)`（兼容带章节序号前缀的父项，如 `4(九) 铁附件、电缆防火封堵` 包含 `铁附件、电缆防火封堵`）。
2. **增加 `tree_level` 严格层级递减约束**:
   - 在前后端挂载循环中加入刚性校验：若双方均存在 `tree_level`，要求候选父节点必须严格处于更高层级（`prev.tree_level < node.tree_level`），彻底杜绝同级兄弟项因名字重叠互相吞并。
3. **单元测试与全量构建验证**:
   - 在 [`tests/unit/test_multilevel_bom_structure.py`](file:///d:/Myproject/bidding_sys/backend/tests/unit/test_multilevel_bom_structure.py) 中新增复合名称兄弟项防吞并与自底向上金额汇总回归测试用例 `test_sibling_item_substring_of_compound_parent_name_hierarchy`；
   - 后端全部单测及 API 接口测试（15 tests）全部通过；
   - 前端 Vite 构建通过（`✓ built in 3.57s`）。

## 树形构建解耦 tree_level 依赖，纯粹以 parent_item 与 root_item 进行精准拓扑挂载

### 1. 变更背景与现象
- **问题反馈**: 用户在智能 BOM 成本测算界面中发现 `(二) 继电保护及安全自动装置` 下属的 `#1 防孤岛及频率电压紧急控制柜` 并没有折叠进父节点，而是作为两个平行的顶层独立节点平铺显示，没有形成折叠父子树。
- **根本原因**:
  - 原本加入的 `levelMatches = prev.tree_level < node.tree_level` 属于过度约束；
  - 大模型在解析表格时，对某些章/节标题和分项都可能填了 `tree_level: 1`，但明确指明了 `parent_item = "继电保护及安全自动装置"`；
  - 强制要求 `prev.tree_level < node.tree_level` 导致当两者均为 `1` 时挂载失败。
  - 实际上，`tree_level` 是树构建完成后的**自派生属性（计算深度）**，不应作为挂载的前置硬性过滤。

### 2. 核心架构重构
1. **纯粹以 `parent_item`、`root_item` 与 `section_name` 进行树拓扑构建**:
   - 前端 [`CostTable.tsx`](file:///d:/Myproject/bidding_sys/frontend/src/components/CostTable.tsx) 与后端 [`cost_service.py`](file:///d:/Myproject/bidding_sys/backend/app/services/cost_service.py) 彻底移除对抽取时 `tree_level` 的前置过滤；
   - 依靠已加固的精确/包含名称匹配（`prevName === parentName || prevName.includes(parentName)`）和反向防短名称吞并规则；
   - 树构建完成后，由 `traverseAndClean` 递归遍历自然计算真实的 `tree_level`（根节点=1，子节点=2，孙节点=3...）。
2. **测试与验证**:
   - 后端全部 15 个单元测试及 API 测试通过（`15 passed in 8.78s`）；
   - 前端 Vite 构建通过（`✓ built in 2.21s`）。

## 修复投标文件格式提取 (extract-bid-format) LLM 返回 table_template 导致的枚举校验异常

### 1. 变更背景与问题定位
- **问题反馈**: 在调用 `/api/v1/bidding/extract-bid-format/{doc_id}` 提取 PDF 标书的格式附件时，后端日志抛出 `LLM 提取投标文件格式 JSON 解析失败: 7 validation errors for BidFormatStructure - sections.*.content_type: Input should be 'form_table', 'text_template', 'checklist' or 'other' [type=enum, input_value='table_template']`，导致大模型提取出的有效格式内容全部丢失，回退至 3 项基础托底结构。
- **根本原因**:
  1. 大模型在提取表格/表单类附件时自发返回了 `"content_type": "table_template"`，而 [`bid_generator.py`](file:///d:/Myproject/bidding_sys/backend/app/schemas/bid_generator.py) 中的 `ContentTypeEnum` 仅定义了 `form_table`，未包含 `table_template` 或同义词容错；
  2. [`bid_generator.py`](file:///d:/Myproject/bidding_sys/backend/app/schemas/bid_generator.py) 模型中缺少 Pydantic 的 `field_validator(mode="before")` 数据清洗逻辑，导致未知或同义词字符串直接触发 ValidationError 异常中断；
  3. [`bid_format_extractor_service.py`](file:///d:/Myproject/bidding_sys/backend/app/services/bid_format_extractor_service.py) 提示词中未对 `content_type` 允许的枚举值做明确枚举约定，且使用的是裸 `invoke` + `json.loads` 而非带有 Markdown 代码块清洗能力的 `generate_json`。

### 2. 核心修复与升级
1. **数据模型 (`app/schemas/bid_generator.py`) 强韧容错升级**:
   - `ContentTypeEnum` 新增 `TABLE_TEMPLATE = "table_template"` 兼容别名；
   - 在 `BidFormatSection` 中新增 `@field_validator("content_type", mode="before")`，将 `table_template`、`table`、`form`、`excel` 等同义词自动规范映射至 `form_table`，将 `doc`、`letter` 等映射至 `text_template`，未识别枚举值降级为 `other`，杜绝因枚举值不匹配引发异常；
   - 为 `section_title`、`body_markdown`、`placeholders` 及 `BidFormatStructure.sections` 增加 `mode="before"` 校验器，兼容 `None`、单一字符串以及字典型列表的自动转换。
2. **提取服务 (`app/services/bid_format_extractor_service.py`) 与导出服务优化**:
   - **Markdown 标题探照灯正则升级**：原正则表达式 `^\s*第...` 无法匹配 MinerU 输出的 `# 第六章 投标文件格式`（以 `#` 开头），导致未命中真实格式章节（位于第 51 页，字符位置约 52,000）并错误回退到前 30,000 字符（包含“投标人须知”文件清单描述，进而生成“原文未提供样张”）。升级为支持 `^[#\s\*]*第\s*[一二三四五六七八九十\d]+\s*[章篇部分卷节]` 与内部空格匹配，精准定位并提取全量格式正文切片；

   - 在 [`llm_service.py`](file:///d:/Myproject/bidding_sys/backend/app/services/llm_service.py) 中增加 `generate_json = generate_structured_json` 兼容别名，提取服务统一切换调用 `self.llm_service.generate_structured_json(prompt, temperature=0.1)`，自动剥离 Markdown 围栏并执行安全解析与 Token 审计；

## 章节 Worker 造价专家工作流 2D 矩阵直通与 LLM 底层网络容错重试优化

### 1. 变更背景与问题定位
- **问题现象**: 用户在进行单章节微调/重新生成（如《投标配置及分项报价表》）时，后台日志显示多次调用 `query_financial_quotation_tool` 并反复输出“成功生成 27 行 BOM 自适应表格 JSON 矩阵”。
- **根本原因**:
  1. **提示词引导冗余与并发 Tool Calls**: 原造价专家 Prompt 在第 1 步引导查询 `cost_estimates`（返回纯文本），在第 3 步要求 2D 矩阵，导致大模型在单轮思考中同时下发了 `cost_estimates` 与 `cost_estimates_json_matrix` 两个并行工具调用；且在已获知目标表格 `/body/tbl[N]` 及表头后，仍按第 1 步说明重复调用 `officecli_query_structure` 进行表格扫描；
  2. **提示词中包含具体业务示例**: 部分规则中包含具体工程/项目名称，未完全遵循抽象占位符标准；
  3. **底层网络波动导致 Agent 状态机重置**: DeepSeek API 遇到网络连接超时时，因底层客户端缺少自动重试，向上抛出 Connection error 触发了 Worker 外层的任务级重试循环，导致 Agent 从初始状态重跑，再次触发了第一轮工具调用。

### 2. 核心优化与重构
1. **造价专家工作流 2D 矩阵直通 (`bid_filler_workers.py`)**:
   - 重构造价专家工作流（`is_pricing`）：明确在已由系统预注入表格路径与真实表头时，**严禁再次调用 `officecli_query_structure` 结构扫描**；
   - 引导模型直接一步调用 `query_financial_quotation_tool(field_key='cost_estimates_json_matrix', header_columns_json='...')` 获取自适应 2D 矩阵，**严禁在表格填报任务中重复查询 `cost_estimates` 纯文本明细**；
   - 获取 2D 矩阵后直接调用 `officecli_fill_table_rows` 一次性全量写盘，实现 1~2 步内极速闭环，大幅降低 Token 消耗与耗时。
2. **彻底消除提示词硬编码与具体数据 (`bid_filler_workers.py`, `bid_db_tools.py`)**:
   - 遵循 Prompt Engineering 黄金标准，将所有具体业务名称与数值全部重构为抽象占位符与通用规则；
   - 工具 docstring 强化表格填报场景下的字段选择优先级说明。
3. **LLM 客户端底层网络自动重试增强 (`llm_service.py`)**:
   - 在 `ChatOpenAI` 客户端初始化中显式配置 `max_retries=3`，使短暂的网络抖动在底层由 httpx 原地重试，防止异常向上传播导致整个 Agent 状态重置与重复从头调用。

## 财务报价清单与 2D 表格矩阵按区域/标段与工程分项自动聚类排序升级

### 1. 变更背景与问题定位
- **问题反馈**: 在生成的《投标配置及分项报价表》中，物料清单顺序出现“工业四区”与“工业二区”交叉乱序穿插（如四区支架/接地/防水 -> 二区组件/逆变器/电缆 -> 四区并网柜/组件 -> 二区加固/辅材...），且规格型号长文本中含多余换行导致表格严重变形。
- **根本原因**:
  - 原招标文件分为多个章节表格（工程量清单、主设备参数等），大模型抽取时按各段出现的顺序平铺入库，未进行区域聚类；
  - `build_dynamic_matrix_for_header` 及明细查询直接按数据库平铺顺序返回，缺乏区域（二区优先/四区其次）及工程专业分项的自动聚类排序。

### 2. 核心算法实现与升级
1. **纯通用区域/标段智能聚类与稳定保序算法 (`sort_cost_items_by_scope_and_hierarchy`)**:
   - **完全杜绝硬编码与具体数据**：不包含任何具体行业（如光伏、建筑等）或特定设备名称（如组件、逆变器等）的死代码；

   - **同区域内部严格稳定保序 (Stable Relative Order)**：同区域内部严格保持从原招标文件/BOM 提取时的自然相对次序，完全忠实于原文件结构；
2. **2D 矩阵与明细查询自动挂载聚类**:
   - `build_dynamic_matrix_for_header` 和 `query_financial_quotation_tool` 统一前置调用聚类排序，确保矩阵与文本明细均条理清晰、同标段/同区域物料连续聚集；
   - 序号列 `__INDEX__` 自动根据新的聚类排序从 1 到 N 自增编号；
   - 规格型号 `spec` / `__BRAND_SPEC__` 字段自动清洗内部多余换行符与制表符，避免 Word 表格因换行被撑高变形。

## 章节 Worker 结构查询会话级缓存与 Prompt 单次提取闭环优化

  1. **Parallel Tool Calling 并行调用**: 大模型在单次决策中针对不同关键词（如同时查询“设备”与“重大违法记录”）同时下发多个 tool call，导致工具在毫秒级内连续被触发；

### 2. 核心优化与重构
1. **Worker 工具层会话级缓存与全量加载提示 (`bid_filler_workers.py`)**:
   - 在 `_build_worker_tools` 闭包内引入 `dom_cache` 会话级缓存，同一 Worker 内重复查询时直接毫秒级命中缓存复用，避免重复文件解析与日志刷屏；

2. **Prompt 全面消除关键词搜索误导与强化闭环法则 (`bid_filler_workers.py`)**:
   - 彻底移除 Prompt 中误导大模型传入 `keyword_filter='...'` 的示例写法，全面更新为 `officecli_query_structure(selector='...')`；
   - 强化【单次扫描与严禁重复查询 — 快速闭环铁律】，明确调用一次即可获得整章全部 DOM 结构，获取后必须立即调用写盘工具提交提案并闭环；

  1. **全量工具 Schema 冗余**: 系统原先将全部 14 个工具（6个DB工具 + 6个Office工具 + 2个RAG工具）完整发给每个 Worker，每个工具的 JSON Schema 定义占用了 1,500 ~ 2,000 Tokens 的 Prompt 开销，而实际每个 Worker 只需 2~4 个工具；
  2. **公文章节调库往返延时**: 简单公文/声明类章节（如封面、投标函、授权书、承诺函）本只需填入企业基本工商信息与项目核心标号报价，却经历 3~4 轮工具交互；且若将企业档案全量泛滥注入给报价表或偏离表等章节，又会导致不需要企业档案的章节产生无关的 Token 浪费。

### 2. 核心架构优化与实现
1. **动态工具包裁剪 (Dynamic Tool Pruning, `bid_filler_workers.py`)**:
   - `_build_worker_tools` 依据章节角色（`mapping_hint` 与 `chapter_title`）动态裁剪工具包：
     - **分项报价专家 (`is_pricing`)**：仅装配 `[officecli_query_structure, query_financial_quotation_tool, officecli_fill_table_rows]`（3 个专用工具，彻底剔除资质、RAG、图片工具）；
     - **商务/技术偏离表专家 (`is_deviation`)**：仅装配 `[officecli_query_structure, get_full_chapter_text, search_bidding_document, officecli_fill_table_rows]`（4 个专用工具，彻底剔除财务、资质、图片工具）；
     - **资质证明专家 (`is_qualification`)**：仅装配 `[officecli_query_structure, query_company_qualification_tool, query_company_profile_tool, officecli_insert_image, officecli_batch_write_slots, officecli_write_slot_value]`（6 个专用工具）；
     - **公文表单专家 (`is_letter_or_form`)**：仅装配 `[officecli_query_structure, officecli_batch_write_slots, officecli_write_slot_value, officecli_batch_fill_sentence, query_company_profile_tool, query_project_metadata_tool]`（6 个轻量工具）；
   - **收益**：每轮请求直接省去 **1,000 ~ 1,500 Tokens** 的无用工具定义描述开销。
2. **定向按需元数据注入 (Targeted Selective Injection, `bid_filler_workers.py`, `bid_filler_agent.py`, `bid_generator.py`)**:
   - 在主流程派发及单章微调前，底层预先读取一次企业主档案与项目核心元数据（标号/报价/工期/质量标准），组装为 `prefetched_metadata`；
   - **仅针对公文函件类章节（封面、投标函、授权书、承诺函、声明函）**：在 User Prompt 中定向注入上述数据，引导 Agent 优先直接收集数据并通过 `officecli_batch_write_slots` 1 轮极速直出，交互轮次从 3~4 轮直降至 1 轮，耗时缩至 1~2 秒；
   - **针对报价表、偏离表、技术方案等章节**：**100% 绝不注入企业基础档案**，彻底避免无关数据的 Token 浪费。

## 彻底清除标书生成中的“(原文无槽位，零改动保留)”及说明性元数据注释

### 1. 变更背景与问题定位
- **问题反馈**:
  - 用户反馈生成的 Word 文档中，无槽位的固定原文段落（如《投标函》致函单位、授权说明、同意条款 1~4 条）末尾被附加了 `（原文无槽位，零改动保留）` 或 `（固定原文，零改动保留）` 等说明性注释。
- **根本原因**:
  1. Worker Agent 在输出操作总结表格（Markdown Table）或 JSON 提案时，针对无需改动的固定段落，在 `实际填入/扩写结果` 或 `proposed_text` 中添加了说明性括号注释；
  2. 提案解析与提取逻辑（`_parse_proposals`）未对这类注释进行程序化剥离，仍将其作为 `sentence_batch` 提案提取；
  3. DOM 写盘引擎（`fill_docx_proposals_in_dom`）在整段替换或插值替换时，直接将包含元数据注释的文本回写至 Word 段落中，导致文本污染。

### 2. 核心架构与清洗防护机制
1. **质检引擎新增通用注释清洗与无操作提案识别 (`review_engine.py`)**:
   - 新增 `clean_zero_change_annotations(text: str) -> str`：
     - 精准匹配并剥离各类 `（原文无槽位，零改动保留）`、`（固定原文，零改动保留）`、`（模板固定原文）`、`（正文已写，零改动）`、`（无需写盘）` 等说明性元数据注释；
     - 严密保护法定业务括号（如 `（法定代表人）`、`（单位盖章）`、`（大写）`、`（元）` 等）。
   - 新增 `is_zero_change_or_no_op_proposal(proposed_text, original_context, prop_type) -> bool`：
     - 深度比对清洗后的提案文本与原文模板，若字符骨架完全一致、文本为空或仅为元数据标记词，自动判定为无操作提案 (No-Op)。
   - 在 `clean_cell_text_value` 中集成 `clean_zero_change_annotations`。
2. **Worker 提示词与提取过滤强化 (`bid_filler_workers.py`)**:
   - 在 `build_worker_prompt` 的【最高铁律】与【输出总结格式要求】中新增明确负面约束，严禁在提议内容或总结表格中附加任何说明性注释，无需修改的固定段落保持原样即可；
   - 在 `_parse_proposals` 解析 Markdown 表格时，实时剥离说明性注释并过滤 No-Op 提案行；
   - 在 `_normalize_proposal_item` 归一化提案时，过滤所有 No-Op 提案。
3. **DOM 写盘与渲染引擎防护 (`bid_filler_agent.py`)**:
   - 在 `fill_docx_proposals_in_dom` 处理单提案与多槽位提案前，统一清洗 `proposed_val`；
   - 比对清洗后的内容与真实 Word 段落文本 `real_text`，若判定为无操作提案，直接跳过段落清空与重写，100% 留存原 Word 原生样式；
   - 在 `_render_diff_paragraph_runs` 与 `proposals_to_commands` 中全面清洗注释并拦截 No-Op 提案。

- 在 [`backend/tests/unit/test_bid_filler.py`](file:///d:/Myproject/bidding_sys/backend/tests/unit/test_bid_filler.py) 中新增：
  - `test_clean_zero_change_annotations_and_no_op_detection`：验证各类零改动注释剥离、业务括号保护及 No-Op 识别；

## 表格分类与填报策略升级（区分固定格式表单与动态展开表，零硬编码原则）

### 1. 业务场景与需求定位

  - 而对于分项清单、设备清单、偏离表等留有较大空白占位行的表格，则必须进行增加行全量展开。
  - 用户特别强调：**严禁在代码、Prompt 与规则中出现任何硬编码词汇（如写死“投标总报价（大写）”、“开标一览表”或具体的金额样例数字）**。

     - **纯几何与结构判定**：不依赖任何硬编码的章节名称或特定价格/字段标签；
     - 判定规则：
       1. 扣除表头后数据行仅 1 行（或总行数较少且末行存在跨多列合并的表尾特征）；
       2. 首个数据行已预置了非空文本描述（非纯空白占位行），仅特定单元格留白；

2. **Worker Prompt 抽象化重构 (`bid_filler_workers.py`)**:

     - **动态多行清单展开表（空位较大，需展开多条明细）**：必须增加行全量展开（Full Matrix Expand），使用 `officecli_fill_table_rows` 全量覆写。

## 成本核算与报价表 CostEstimate 品牌/型号/厂家字段精准对齐与空值纯净留空优化

### 1. 变更背景与问题定位

  - 用户反馈生成的 Word 投标文件中，《投标配置及分项报价表》中的【品牌、规格、型号】一栏被填入了招标文件原文的长篇技术参数要求（如 300 多字的光伏组件衰减率/效率/STC 测试条件），且【生产厂家】显示为“未指定品牌”，与前端页面中对标匹配出的具体型号（如 `天合光能 635Wp`、`华为 110kW`）对应不上；
  - 用户明确要求：**仅采用价格库对标匹配或用户手动填写的品牌、型号与厂家，若无匹配/未指定，则直接留空（`None` / `""`），绝对不要回退采用标书的冗长要求文字或“未指定品牌”**。
- **根本原因**:
  1. [`analysis.py`](file:///d:/Myproject/bidding_sys/backend/app/api/endpoints/analysis.py) 与 [`cost_agent.py`](file:///d:/Myproject/bidding_sys/backend/app/agents/nodes/cost_agent.py) 在向 `cost_estimates` 数据表落盘时：
     - `brand` 字段优先取了标书的 `brand_requirements`（如“未指定品牌，需满足认证要求”），导致具体品牌被冲掉；
     - `spec` 字段存入了标书原文技术指标 `spec_requirement`（几百字的长文本），导致价格库具体型号 `matched_model` 丢失；
     - `analysis.py` 保存接口中漏掉了 `manufacturer` 字段的写入；
  2. [`bid_db_tools.py`](file:///d:/Myproject/bidding_sys/backend/app/agents/tools/bid_db_tools.py) 在组装【品牌、规格、型号】合并列时，若规格字符串本身已以品牌开头，直接拼接会导致“品牌 品牌 型号”的冗余重复。

### 2. 核心修复与升级
1. **落盘字段优先级调整与标书长文本回退剥离 (`cost_agent.py`, `analysis.py`)**:
   - `effective_brand`：仅取 `matched_brand` 或用户填写的 `brand`，无则直接留空为 `None`，彻底剥离 `brand_requirements`（如“未指定品牌”）；
   - `effective_model`：仅取 `matched_model` 或 `model`，无则直接留空为 `None`，彻底剥离几百字的标书长文本 `spec_requirement`；
   - `effective_mfg`：仅取 `matched_manufacturer` 或 `manufacturer`，无则直接留空为 `None`；
   - 补全 `analysis.py` 中的 `manufacturer` 落盘字段。
2. **2D 矩阵生成引擎合并列去重与纯净格式化 (`bid_db_tools.py`)**:
   - `build_dynamic_matrix_for_header` 提取【品牌、规格、型号】（`__BRAND_SPEC__`）时，若规格字符串开头已包含品牌名（如 `spec="华为 SUN2000-110KTL"`），自动去重输出 `华为 SUN2000-110KTL`，避免重复拼接；
   - 纯净处理空值，若品牌或型号为空则直接显示非空部分或留空，Word 表格不再被长文本撑大变形。
