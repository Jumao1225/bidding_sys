## 智能 BOM 成本测算卡片宏观工程大类标准化与多级树形收敛修复

### 1. 变更背景与问题
- **现象**: 在前端 `CostTable` 智能 BOM 成本测算卡片中，顶部区域筛选栏出现了 14 个零散碎片化标签（如“一次侧部分-10kV高压设备”、“调度自动化及二次安防”、“一体化电源”、“智能辅助控制系统”等），将原本同属于《二次侧部分》名下的子装置割裂成了并列的平级标签。
- **根因**:
  1. 大模型在前期提取时将表格局部的二级小标题误填入 `section_name`。
  2. 前端 `CostTable.tsx` 之前直接按未清洗的 `section_name` 生成筛选 Tag，缺少大类收敛机制。

### 2. 核心修复与升级
1. **前端工程大类智能收敛与排序 (`CostTable.tsx`)**:
   - 新增 `normalizeSectionName` 函数，建立确定性宏观大类归口引擎，将包含“一次侧/高压/箱变”、“二次/自动化/调度/电源/安防/监控/通信”、“智能通讯”、“直流侧/组件/逆变器”、“土建/桩基/支架”等关键词的碎片化字串，确定性收敛归纳至标准的 5 大顶级工程大类：
     - `项目需求清单（一次侧部分）`
     - `项目需求清单（二次侧部分）`
     - `项目需求清单（智能通讯部分）`
     - `项目需求清单（直流侧太阳能板、逆变器等）`
     - `项目需求清单（土建配套部分）`
   - 对筛选按钮加入 `SECTION_ORDER` 规范化排序，并将每个大类下的物料统计项数精准对齐。
2. **后端与落盘双重对齐 (`table_utils.py`, `cost_agent.py`, `analysis.py`)**:
   - 在 `table_utils.py` 中新增 `normalize_section_name` 函数；
   - 在 `cost_agent.py` 与 `analysis.py` 更新 `CostEstimate` 与测算数据时，同步调用归一化函数，确保数据库落盘数据与前端视图保持一致。
3. **空值与未分区场景 (`section_name == null`) 的三重防御与优雅兼容机制**:
   - **机制 1 (父级继承)**: 内部子元器件若自身 `section_name` 为空，在构建树形时自动向上继承其所属父节点/箱变/开关柜的宏观大类，确保不脱节；
   - **机制 2 (混合兜底)**: 当标书中存在其他明确分部，而某些独立散项（如手动追加的现场服务费）无分部时，自动归入 `通用及其他分项`，并在顶部提供独立筛选标签；
   - **机制 3 (纯单体项目)**: 若全篇标书所有条目均无分部划分，顶部自适应隐藏区域筛选栏，全量平铺整棵树，避免出现冗余单个标签。

### 3. 验证结果
- 单元测试 `tests/unit/test_multilevel_bom_structure.py` 和 `tests/unit/test_cost_agent.py` 全量 10 个测试用例全部通过（10 passed）。

## 智能 BOM 对标匹配 Agent (CostAgent) 极致瘦身与上下文重构

### 1. 变更背景与性能瓶颈
- **痛点 1 (Input Tokens 严重浪费)**: 原逻辑在并发处理每个批次（100项/批）时，向大模型重复广播发送长达 31KB 的 RAG 检索原文（包含大量全文段落），白白浪费了 6~8 万 Input Tokens。
- **痛点 2 (Output Tokens 极高 & 截断风险)**: 输出 Schema 要求大模型原封不动复述 18 个字段（包括数千字的技术规格要求、父子关系、层级、工程大类等），导致单批输出直接顶破 4096 Output Token 上限，频发 502/截断报错。
- **痛点 3 (四则运算偶发幻觉)**: 成本小计（`qty * ref_price`）交由大模型计算，速度慢且存在浮点乘法精度偏差。

### 2. 核心架构重构方案
1. **输入端极致精简 (零 RAG 广播)**:
   - 彻底移除 Prompt 中的 31KB 重复 RAG 原文广播；
   - 仅向大模型注入当前批次待对标的精炼设备要素（`item_index`, `name`, `specifications`, `quantity`, `unit`, `parent_item`, `brand_requirements`）及 BM25 动态精选的 Top 40 自有价格条目；
   - 单批输入 Token 消耗暴降 80% 以上。
2. **输出端精简 Schema (`BatchMatchResult` + `ItemMatchOutput`)**:
   - 大模型输出 Schema 从 18 个重型字段降维至 6 个核心对标字段（`item_index`, `ref_price`, `matched_name`, `matched_brand`, `matched_model`, `matched_manufacturer`, `match_quality`, `comparison_note`, `warning`）；
   - 单批输出 Token 消耗从 4000+ 暴降至 300~500 Tokens，彻底消除截断与超时。
3. **本地 Python 确定性拼装与死锁保护**:
   - 由本地 Python 循环根据 `item_index` 将大模型的对标匹配结果与 `EngineeringMetadata` 中的原始设备树数据 100% 锁死合并；
   - 在本地安全执行打包置零防重规则与浮点乘法小计（`subtotal = round(qty * ref_price, 2)`）及总价聚合；
   - 完美兼容历史数据结构与已有单元测试 Mock。
4. **批次微切分 (`BATCH_SIZE = 30`)**:
   - 将批次大小从 100 项调优为 30 项，配合 5 路并发 ThreadPoolExecutor，339 项物料全量测算时间从 40s+ 缩短至 5~8 秒。

### 3. 验证结果
- 全量单元测试 `tests/unit/test_multilevel_bom_structure.py` 及 `tests/unit/test_cost_agent.py` 10 个测试用例全部绿灯通过（`10 passed in 9.94s`）。

## 智能 BOM 成套母项自底向上（Bottom-Up）自动金额汇总与防双重计费升级

### 1. 变更背景与问题
- **问题反馈**: 用户在智能 BOM 成本测算表格中将成套主标的物（如“导体和导线”）下的所有子项（如多规格电缆、终端等）单价与总价填写完毕后，母项行仍然显示 `--`（单价 `--`、小计 `--`、未匹配）。
- **根本原因**:
  1. 初始解析时，企业价格库无整包打包库价，母项自身价格为 0。
  2. 前端表格原按行独立读取自身 `ref_price` 与 `subtotal`，缺少“自底向上（Bottom-Up）”的树形递归聚合计算。
  3. 顶层预估总成本（Total Cost）原使用扁平 items 遍历累加，若简单累加母项会导致母项与子项双重计费（Double-Counting）。

### 2. 核心架构与逻辑升级
1. **树形自底向上后序遍历计算 (`CostTable.tsx`, `cost_service.py`)**:
   - 当父节点（成套主标的物/总成项）自身未直接指定独立打包统价，而子项有计算金额时，自动将所有直接子节点 `subtotal` 递归累加为父节点的 `subtotal`（支持任意 N 级嵌套）；
   - 自动折算父节点参考单价：`parent.ref_price = parent.subtotal / parent.qty`；
   - 匹配置信度标签自动标记为 `成套汇总`，并在匹配说明中展示“已根据下属 N 个分项/元器件单价与工程量自底向上汇总测算”。
2. **顶层预估总成本精准收敛 (防双重计费)**:
   - 全局总成本 `total_cost` 严格基于所有顶层根节点（Root Nodes，Level 1 或 parent_item 为空）的 `subtotal` 求和；
   - 彻底杜绝父节点与子节点重复累加，确保数学上严密闭环。
3. **前端 0 延迟实时联动与高亮渲染 (`CostTable.tsx`)**:
   - 在用户行内修改子项单价/数量时，母项的小计、折合单价以及顶部预估总成本 0 延迟即时联动刷新；
   - 成本小计栏为母项增加专属深蓝高亮与“成套总计”标签。
4. **后端接口与 Agent 同步支持 (`analysis.py`, `cost_agent.py`)**:
   - 新增 `app/services/cost_service.py` 通用层级计算服务；
   - `PUT /api/v1/analysis/{document_id}/cost-analysis` 保存接口与 `CostAgent` 测算节点统一调用 `rollup_hierarchical_cost_items`，确保数据落盘与前端视图 100% 一致。

### 3. 测试与验证
- 新增 API 单元测试 `test_update_cost_analysis_hierarchical_rollup_for_parent_items`；
- 全量后端测试用例 `tests/api/test_cost_analysis_update_api.py`、`tests/unit/test_cost_agent.py`、`tests/unit/test_multilevel_bom_structure.py` 全部通过（`14 passed`）；

## 修复子项二次修改时成套母项价格锁死不联动的 Bug

### 1. 根本原因
- 当母项在首次保存落盘后，其状态被标记为 `match_quality: 手动修改`，且自身存有旧的 `ref_price`；
- 在二次修改下属子项单价时，前端与后端原判断逻辑误将带有“手动修改”标签的母项判定为“具有用户独立指定的固定整包单价”，未触发子项新总价覆盖，导致母项价格锁死在旧值。

### 2. 修复方案
- 确立**子项优先动态汇总原则**：只要成套母项下属的子项总金额 `childrenSubtotalSum > 0`（且当前未在直接编辑该母项自身），成套母项的金额**强制 100% 由所有直接子项实时求和动态驱动**；
- 同步更新前后端 `CostTable.tsx` 与 `cost_service.py`，彻底消除二次修改子项时母项不联动的 Bug。
