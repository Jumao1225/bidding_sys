# 项目改动日志 - 2026-08-03

## 📋 变更摘要
针对文档解析提取引擎 (`ExtractorService`) 进行策略重构，实现了 **招标文件（`general`）与投标文件（`bid`）解耦的多通道文本切片逻辑**。复刻了上一版本（Commit `c307c34`）的招标文件宏观章节切块策略，解决了由于 TOC 目录白名单过敏导致的招标文件切片过度碎片化问题。

- **文件路径**: [backend/app/services/extractor_service.py](file:///d:/Myproject/bidding_sys/backend/app/services/extractor_service.py)
- **主要改动**:
  1. **大章划分模式隔离 (`_group_markdown_text_by_chapter` & `_detect_major_chapter_in_line`)**：

### 8. OfficeCLI 路径精准度校验与表头保护防护 (`bid_filler_agent.py` & `bid_filler_workers.py`)
- **问题根因分析**: 当 Worker 生成粗粒度的表格容器路径（如 `/body/tbl[1]`）时，如果简单将其盲目补全为第一行第一列（`/tr[1]/tc[1]/p[1]`），极易误覆盖表格的“表头标题文本”（如将“序号/标的物名称”等表头给盖掉）。
- **优化与精准保证说明**:
  1. **硬核拦截防护**：在 [bid_filler_agent.py](file:///d:/Myproject/bidding_sys/backend/app/agents/bid_filler_agent.py) 的 `proposals_to_commands` 函数中，对止步于 `/tbl[N]` 或 `/tr[N]` 的容器路径进行强校验拦截，严禁盲目向表头写入数据。
  2. **单元格层级精密补全**：仅对定位到具体单元格 `/tc[N]` 的路径补全 `/p[1]`，确保所有数据精准填入对应单元格内部，绝不越界。
  3. **源头 Prompt 精准规约**：在 [bid_filler_workers.py](file:///d:/Myproject/bidding_sys/backend/app/agents/bid_filler_workers.py) 的 Prompt 中下达强指令，约束大模型必须精确导出 `/tr[ROW]/tc[COL]/p[1]`，彻底确保修改原文的 100% 准确性。

### 9. 标书填报原文字段与标签绝对保护修复 (`bid_filler_agent.py` & `bid_filler_workers.py`)
- **问题根因分析**: 当标书包含形如 `投标人名称（单位盖章）：________________`、`法定代表人（签字）：________________`、`地 址：________________` 的填报字段时，Worker 倾向于仅输出孤立的填报数据值（如 `"北京某某科技有限公司"`），且 `proposals_to_commands` 将其转换为 OfficeCLI 的 `set` 命令，导致整个段落文本被全量覆盖，原有的字段标签（如 `"投标人名称（单位盖章）："`）被擦除丢失。
- **优化与精准保证说明**:
  1. **Worker Prompt 标签强规则保护**：在 [bid_filler_workers.py](file:///d:/Myproject/bidding_sys/backend/app/agents/bid_filler_workers.py) 的 Prompt 中下达【原文标签前缀绝对保护法则】，要求 `proposed_text` 在有标签时必须保留完整的前缀标签。
  2. **命令转换器标签自动补全**：在 [bid_filler_agent.py](file:///d:/Myproject/bidding_sys/backend/app/agents/bid_filler_agent.py) 的 `proposals_to_commands` 中引入 `_extract_label_prefix` 前缀提取与正则校验机制。即便 Worker 输出了孤立的数据值，系统会在转换为写盘命令前自动提取 `original_context` 中的字段标签并合并补齐（如合并为 `"投标人名称（单位盖章）：北京某某科技有限公司"`），100% 确保原标书的字段与文本不丢失。
  3. **单元测试验证**：在 `test_bid_filler.py` 中补充了针对 `_extract_label_prefix` 与前缀防擦除自动合并的单元测试，确保逻辑稳定且通过所有断言。

### 10. 标书填报下划线美化与原生格式继承修复 (`bid_filler_agent.py`)
- **问题根因分析**: OfficeCLI 在执行 `set` 节点写盘命令时，会将段落整体作为单条 Run 纯文本写入，抹除了原有 Word 节点的 Run 拆分与 `underline=True` 下划线格式，导致填报后的字段值失去了下划线。
- **优化与精准保证说明**:
  1. **下划线继承美化器 (`_apply_underline_to_filled_doc`)**：在 [bid_filler_agent.py](file:///d:/Myproject/bidding_sys/backend/app/agents/bid_filler_agent.py) 中引入 DOM 级格式美化器。写盘完成后自动遍历提案节点，将段落精准拆分为无下划线的前缀标签 Run (`underline=False`) 与带下划线的填报数据 Run (`underline=True`)。
  2. **日期与槽位拆分**：针对 `____年___月___日` 拆分填充字段，精准为数字施加 `underline=True`、为“年月日”汉字保持 `underline=False`。
  3. **单元测试验证**：在 `test_bid_filler.py` 中新增 `test_apply_underline_to_filled_doc_should_set_underline_on_value_run` 测试用例，断言通过。

### 11. 标书 DOM 级原位填报与原文标签绝对防护升级 (`bid_filler_agent.py`)
- **问题根因分析**: 之前的写盘逻辑在转换为 OfficeCLI 指令时，仅从 Worker 输出的 `original_context` 文本做前缀正则表达式提取。如果 Worker 提取的上下文缺失了标签字符，OfficeCLI 的 `set` 命令就会将对应段落/单元格全量重写为孤立的填报值，导致原标书的字段标签（如 `"投标人名称（单位盖章）："`）在写盘时被覆盖删除。
- **优化与精准保证说明**:
  1. **DOM 级原位填报引擎 (`fill_docx_proposals_in_dom`)**：弃用简单的全量文本覆写，改由 Python DOM 引擎在写盘前直接读取磁盘 `.docx` 中目标 XPath 节点的**真实 Word 原文**。
  2. **双重前缀提炼**：通过 `_extract_prefix_from_text` 优先从真实 Word 节点提炼前缀标签（如 `"投标人名称（单位盖章）："`），哪怕 Worker 的 `original_context` 字段缺失，也 100% 确保不会擦除原标书中的任何标签与文本。
  3. **原位 Run 拆分与下划线强注入**：单次遍历原位将段落重构为：[前缀标签 Run (无下划线)] + [填报数据 Run (带 OpenXML `<w:u w:val="single"/>` 原生下划线)]，一次性完美解决“覆盖原文”与“丢失下划线”两个痛点。
  4. **单元测试验证**：在 `test_bid_filler.py` 中新增 `test_fill_docx_proposals_in_dom_should_preserve_real_labels_and_add_underline` 单元测试，17/17 测试全部通过。
