## 标书生成与表格回填（BidFiller）2D 矩阵写盘与技术偏离表修复

### 1. 问题背景
在标书回填 Word 过程中，【技术要求响应及偏离表】等长章节 Worker 成功检索并生成了多行技术响应条款（通过 `officecli_fill_table_rows` 提交 2D 矩阵），但最终生成的 Word 文件中偏离表仍为空白。

### 2. 根本原因定位
1. **字符串断言阻断**：主控 Agent 的 `fill_docx_proposals_in_dom` 中，原逻辑使用严苛的 `p_val.startswith("[[")` 进行表格提案过滤；
2. **格式化换行拦截**：大模型或工具序列化输出带有换行符和缩进的 JSON（如 `"[\n  [\"光伏组件...\"`），导致 `startswith("[[")` 返回 `False`；
3. **提案静默丢弃**：由于被误判为非表格提案，且后续单槽位处理又因 `[` 开头跳过，导致偏离表等 2D 矩阵提案在写盘阶段被 100% 静默忽略。

### 3. 改动明细
1. **`backend/app/agents/bid_filler_agent.py`**：
   - 重构 `fill_docx_proposals_in_dom` 对 `table_rows` 2D 矩阵的识别与解析逻辑，取消脆弱的字符串前缀匹配；
   - 采用稳健的 JSON 解析与二维列表校验，完美兼容带换行、缩进及对象化 2D 矩阵的任意格式；
   - 优化表头列与序号自动对齐机制，未包含序号列时自动在第 1 列补齐 1..N 递增序号；
   - 增加表格无法解析时的清晰告警日志。
2. **`backend/app/agents/bid_filler_workers.py`**：
   - 升级 `_parse_proposals` 中对 `table_rows` 的类型推断，支持反序列化检验与 `/body/tbl[N]` 物理路径判定。
3. **`backend/tests/unit/test_bid_filler_worker.py`**：
   - 新增 `test_fill_docx_proposals_in_dom_formatted_json_matrix_deviation_table_should_succeed` 单元测试，验证格式化换行 JSON 偏离表提案 100% 成功刷盘到 Word。

### 4. 验证结果

## 偏离表伪语法污染拦截与 Tool-First 提案保护加固

### 1. 问题背景
图片反馈显示：技术偏离表第 1 行第 3 列被填入了 `"其他辅材技术要求 + 服务承诺 + '无' + '完全响应招标文件要求，无偏离。'"` 概括文本，第 2 列及后续行全空。

### 2. 根本原因定位
1. **提案覆盖顺序颠倒**：Worker 提案双路融合时，文本提取提案后遍历，覆写了工具调用捕获的权威 2D 矩阵；
2. **大模型偷懒伪语法误提取**：大模型在终端总结里输出了带 `+` 拼接的概括性描述，被 `_parse_proposals` 当作文本提案错误提取并写入单元格。

### 3. 改动明细
1. **`backend/app/agents/bid_filler_workers.py`**：
   - 确立 **Tool-First 原则**：工具捕获的结构化提案（2D 矩阵）具有最高权威，并在有整表提案时自动清理文本误提取的行级伪提案；
   - 彻底废除特定业务关键词黑名单，采用**纯通用抽象语法规则**：
     * 规则 1：通用运算符表达式校验，过滤大模型伪拼接字符串（`\S\s*\+\s*\S`）；
     * 规则 2：通用元数据状态词过滤（`—`, `同上`, `略`, 状态标记等）；
     * 规则 3：表格路径与类型严格归一化：整表路径必须为合法 2D 矩阵，行级路径（未指定单元格 `tc`）严禁作为单文本写入，防止错列。
   - 强化通用 Prompt 指引，严禁大模型输出伪语法。
2. **`backend/app/agents/bid_filler_agent.py`**：
   - 彻底移除对特定行业报价 BOM 表的硬编码查询，保持表格引擎对全行业所有类型表格的 100% 纯粹通用性。
3. **`backend/tests/unit/test_bid_filler_worker.py`**：
   - 使用抽象通用占位符（`条款A`、`条款B`）进行单元测试，验证伪语法被 100% 通用规则拦截。

### 4. 验证结果

## 实质性要求对照表单单元格提案双路融合保护修复

### 1. 问题背景
运行后《技术要求响应及偏离表》已正常填入内容，但《第四章项目需求中实质性要求响应对照表》在生成的 Word 文档中除最后 1 格外其余内容全部为空白。经诊断报告确认：大模型已完整分析并生成了 20 个单元格全部 10 项实质性要求与“是”响应提案，但写盘后内容丢失。

### 2. 根本原因定位
1. **整表路径正则锚点缺失**：Worker 在执行【Tool-First 双路提案融合】时，原逻辑使用 `re.search(r'^(/body/tbl\[\d+\])', p_path)` 判断是否为整表 2D 矩阵提案；

### 3. 改动明细
1. **`backend/app/agents/bid_filler_workers.py`**：
   - 严格整表路径判定：增加必须为 `table_rows` 类型或全字精确匹配 `^/body/tbl\[\d+\]$` 的前置约束；
   - 确保单单元格级提案（`/body/tbl[N]/tr[X]/tc[Y]/p[Z]`）在双路融合时 100% 安全合并保留，互不误删；
   - 优化行级模糊路径过滤规则，放行 `sentence_batch` 与含多列分隔符的行级提案。
2. **`backend/tests/unit/test_bid_filler_worker.py`**：

## 预设标的物模板表（如供货一览表）原位覆盖与表尾汇总误判修复

### 1. 问题背景
图片反馈显示：《供货一览表（主要标的物）》生成后，上方生成了 14 行已填写的全新数据行，而原模板中预置了货物名称与斜杠的 14 行模板行却被挤到了表格最末尾，且全部保持空白未填。

### 2. 根本原因定位
1. **预设数据行误判为表尾汇总行（Footer）**：
   在 `fill_docx_proposals_in_dom` 的 2D 矩阵写盘逻辑中，原代码通过从后往前倒序遍历，只要检测到某一行单元格非完全空白（`not is_blank_data_row`），就直接将其索引作为 `footer_start_idx`；
2. **倒序扫描将整表误判为 Footer**：
   由于《供货一览表》原模板每行都预填了货物名称（如“光伏组件”）和数量斜杠（“/”），导致倒序扫描一直判定为“非空白行”，一路将 `footer_start_idx` 更新到了第 1 行；
3. **全部数据被强制插入到原模板上方**：
   后续 `target_row_idx < footer_start_idx`（`1 < 1`）判定为 False，导致引擎将所有 14 行新数据通过 `add_row` 插入到原模板行上方，把原有的 14 行模板挤到了最底部残留。

### 3. 改动明细
1. **`backend/app/agents/bid_filler_agent.py`**：
   - 彻底移除所有表尾关键词硬编码，重构为**纯 DOM 结构化拓扑检测**（`_is_table_footer_row`）：
     * 基于 OpenXML 底层单元格几何拓扑（物理单元格数 `< total_cols` 或显式声明 `w:gridSpan > 1` 跨列合并）精准识别合并汇总/落款行；
     * 对物理列数完整的标准网格数据行（如包含序号、货物名称等 14 行）判定为普通数据行；
   - 确保预设货物名称/序号的模板行能够 100% 在原行位置精准原位覆盖刷新（In-place Overwrite），总行数严格保持 14 行不变。
2. **`backend/tests/unit/test_bid_filler_worker.py`**：
   - 新增 `test_fill_docx_proposals_in_dom_prefilled_items_table_should_overwrite_in_place_without_duplication` 单元测试，严格验证 14 行预设货物名称/斜杠表格 100% 原位填满，总行数保持 15 行（1 表头 + 14 行数据），无任何多余行残留。

### 4. 验证结果

## 标书正文段落槽位填报重复与残留占位符修复（Diff 级高保真下划线渲染）

### 1. 问题背景
用户反馈在生成的 Word 标书公文段落（如《投标函》主句）中出现文本重复与占位符残留：
> ”根据贵方的                   号招标文件，正式授权下述签字人       根据贵方的RXCG2026-G003号招标文件，正式授权下述签字人李四（授权代表）代表我方四川石楠建设工程有限公司，全权处理本次项目投标的有关事宜代表我方                           （投标人的名称），全权处理本次项目投标的有关事宜。“

### 2. 根本原因定位
1. **提议类型在总结阶段降级**：
   Worker 在 Markdown 明细表中将段落标记为 `sentence_batch`（整句覆盖重写），但在最终总结的 JSON 列表里输出了 `"type": "text"`。融合解析时被当作普通单槽位文本处理。
2. **整段文本误触单槽位切片**：
   写盘引擎 `fill_docx_proposals_in_dom` 匹配到了段落中的第 1 个空格/下划线占位符，执行了 `before_text + proposed_val + after_text` 切片拼接，导致整句话被错误强插在第一个占位符中间，引发前缀重复、整句嵌入、后缀重复与未填槽位残留。
3. **句末正常标点被误剔除**：
   `review_engine.py` 的 `clean_all_ellipsis` 在清理末尾省略号时使用正则误删了正常的单个句号标点 `。`。

### 3. 改动明细
1. **`backend/app/agents/bid_filler_agent.py`**：
   - **新增 `_is_full_paragraph_replacement` 智能判定器**：
     * 支持显式类型（`sentence_batch` / `paragraph` 等）；
     * 引入**首尾双锚点重合匹配**（开头 4~6 字与结尾 4~6 字均相同）；
     * 引入**切片防嵌套防重复拦截**：若待替换值已包含原段落前缀或后缀核心词，立即阻断单槽位切片，升级为整段覆盖；
     * 结合模板骨架词覆盖率与 SequenceMatcher 相似度综合判定。
   - **新增 `_render_diff_paragraph_runs` 高保真 Diff 分段渲染引擎**：
     * 基于 `difflib.SequenceMatcher` 自动比对模板原文与填报文本；
     * 模板固定文字（`equal`）-> 渲染为**宋体小四 12pt 无下划线**；
     * 新填入的业务数据（`replace` / `insert`）-> 渲染为**宋体小四 12pt 原生下划线**；
     * 彻底消除文本重复与未填槽位残留，完美还原标准公文排版。
2. **`backend/app/agents/bid_filler_workers.py`**：
   - 优化 `_parse_proposals` 提炼与融合机制：当 JSON 中的 `type` 为 `"text"` 而 Markdown 表格中指定了 `sentence_batch` 等更精确类型时，自动提升并继承 Markdown 中的提议类型。
3. **`backend/app/agents/review_engine.py`**：
   - 优化 `clean_all_ellipsis` 省略号清理正则，仅清理真正的连续点号/省略号（如 `...` / `……` / `。。`），安全保留合法的单个句末标点。
4. **`backend/tests/unit/test_bid_filler_worker.py`**：
   - 新增 `test_fill_docx_proposals_in_dom_full_paragraph_should_not_duplicate_text` 单元测试，验证多槽位段落整句替换无重复、占位符完全消除且数据带下划线；

## BOM 成本测算与人工修改限价关联及超额强视觉熔断警报修复

### 1. 问题背景
用户在前端人工修改 BOM 清单报表（修改单价、数量或新增费用分项）后，即便预估总成本已明显超出最高投标限价或采购预算，看板仍不显示任何“超额”警报，存在由于超限价导致标书被直接一票否决废标的严重隐患。

### 2. 根本原因定位
1. **后端限价查询脱节**：
   - 招标文件解析时，`financial_service` 提取的最高投标限价（`max_price_limit`）与采购总预算（`budget`）保存在 `FinancialMetadata` 实体表中；
   - `analysis.py:update_cost_analysis` 与 `cost_agent.py` 仅从 `parsed_metadata.get("budget_limit")` 查找，导致返回值恒为 `None`，预算状态始终被赋值为 `"预算未设置"`；
2. **前端缺乏基于最高限价的实时动态判定**：
   - `CostTable.tsx` 未接入 `financial` 财务防线数据，在用户编辑单价/数量时只更新了本地总价，未实时拿总价与最高限价比对；
   - 且当后端返回 `"预算未设置"` 时，前端条件渲染直接隐藏了状态徽标。

### 3. 限价与预算比对业务规则
确立招投标行业标准的判定优先级：
- **第一优先级（核心废标红线）**：以**【最高投标限价 (max_price_limit)】**为第一准绳（超限即废标）；
- **第二优先级（资金池基准）**：若未单独设最高限价，以**【采购总预算 (budget)】**为第二准绳；
- **第三优先级（兼容兜底）**：以 `doc.parsed_metadata.get("budget_limit")` 为兜底。

### 4. 改动明细
1. **`backend/app/api/endpoints/analysis.py`**：
   - 在 `update_cost_analysis` 中增加对 `FinancialMetadata` 的级联查询（`max_price_limit` > `budget` > `budget_limit`）；
   - 精准计算总成本使用率与超额金额，输出规范的 `budget_status`、`budget_numeric`、`limit_type` 与 `budget_limit`。
2. **`backend/app/agents/nodes/cost_agent.py`**：
   - 升级 `cost_node` 成本核算逻辑，同步实现从 `FinancialMetadata` 级联读取最高限价并判定超额。
3. **`frontend/src/pages/AnalysisDashboard.tsx`**：
   - 将 `financial`（核心财务防线）数据作为属性透传给 `<CostTable />`。
4. **`frontend/src/components/CostTable.tsx`**：
   - 接收 `financial` 属性并基于优先级解析出基准限价（最高投标限价 / 采购总预算）；
   - 在行内编辑单价、数量或新增费用时，实现**全实时动态比对**：
     * **超额熔断**（总价 > 限价）：触发红色高亮徽标与 **🚨【强视觉熔断警报】废标风险红线横幅**（实时标明超额金额与超出幅度）；
     * **高风险预警**（使用率 ≥ 90%）：触发黄色警报；
     * **安全范围**（使用率 < 90%）：显示绿色可控标识；
   - 实时总成本卡片同步标注计算基准（最高投标限价与采购总预算双重对照）。
5. **`backend/tests/api/test_cost_analysis_update_api.py`** & **`backend/tests/unit/test_cost_agent.py`**：
   - 新增针对最高投标限价超额、预算可控等场景的 API 与单元测试。
