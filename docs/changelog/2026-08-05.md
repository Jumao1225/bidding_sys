# Change Log (2026-08-05)

### 1. Worker 子 Agent 自定义指令注入 (`bid_filler_workers.py` & `bid_filler_agent.py` & `bid_generator.py`)
- **功能说明**: 支持从前端传入自定义填写指令，透传到每个 Worker 子 Agent 的提示词中。
- **两种注入方式**:
  1. **全局自定义指令 (`custom_instructions`)**: 注入到所有 Worker 的 system prompt 末尾。适用于统一要求（如 "所有日期统一填写为 YYYY年MM月DD日"）。
  2. **按章节类别指令 (`category_hints`)**: 仅注入到匹配 `category` 或 `mapping_hint` 的 Worker。适用于特定章节要求（如 `{"pricing": "报价表中所有单价按 XXX 折测算"}`）。
- **数据流**: `POST body → BidFillRequest → BidFillerState → agent_fill_node → dispatch_chapter_workers → run_chapter_worker → build_worker_prompt → Worker System Prompt`。
- **向后兼容**: 所有新增参数均为可选（`Optional`），不传则行为与旧版完全一致。

### 2. 全代码库 Prompt 防幻觉与杜绝锚定效应抽象化重构 (`bid_filler_schema.py` & `bid_filler_workers.py` & `bid_filler_agent.py` & `review_engine.py`)

  - `bid_filler_workers.py`: 将【防幻觉与伪造日期封杀法则】中的示例替换为 `YYYY年MM月DD日`、`XXX公司全称`。

### 3. 表格单元格填报污染治理与偏离表规范化三层防御架构 (`review_engine.py` & `bid_filler_agent.py` & `bid_filler_workers.py`)
- **问题场景**: 表格填报中，Worker LLM 易受提问上下文干扰在单元格中带入 `序号 1 行，答：无` 等污染前缀，且偏离表【有无偏离】栏填报不符合标书【注2】规约。
- **三层治理体系**:
  1. **第 1 层（DOM 写盘程序强洗）**: 在 `fill_docx_proposals_in_dom` 中识别 `is_in_table = True` 节点，强行应用 `clean_cell_text_value` 正则截断剔除 `序号 X 行`、`答：` 等问答前缀，且单元格内不注入段落级标签前缀。
  2. **第 2 层（Worker Prompt 禁令）**: 在 Worker Prompt 硬约束中下达【表格单元格污染前缀禁令】与【偏离表规范】，要求对于“有无偏离”一栏，无偏离时必须且只能填 `无`，有偏离填 `有`。
  3. **第 3 层（R7 表格污染检测管线）**: 在 `review_engine.py` 中新增 **R7 管线 (`check_table_cell_cleanliness`)**，自动识别单元格提案中的污染前缀并由 R6 自动纯化修正。
- **单元测试**: 新增 `TestCheckTableCellCleanliness` 覆盖前缀剥离与偏离表归一化算法，全量 30 项测试通过。

### 4. 结构化短字段长文本错填熔断与 Review Agent 智能基准算法升级 (`review_engine.py` & `bid_filler_agent.py` & `bid_filler_workers.py`)
- **问题根因分析**:
  1. Worker Agent 误将《授权委托书》首段整句长文本（`根据贵方的...授权...代表我方四川石楠...全权处理...`）当作了落款`投标单位名称：`槽位的填写建议。
  2. 原 R2 一致性检查死板地以数组第一个元素 `all_values[0]` 为基准，当第一条被大长句污染时，导致审查反而把后续正确的公司名都误改成了污染的长句子。
- **四重拦截修补体系**:
  1. **升级 R2 智能基准筛选算法 (`_select_best_clean_value`)**: 排除超过 35 字或包含“根据/授权/处理”的句子大长文，优先选择最短且合规的实体名称做修正基准。
  2. **新增 R8 规则管线 (`check_short_field_text_overflow`)**: 自动检测“投标单位名称/投标人名称/法定代表人”等结构化短字段，若误填长文大句直接报 `R8-TEXT-OVERFLOW` 严重错误并提取纯净公司名自动修正。
  3. ** Worker Prompt【落款与名称字段长文错填封杀令】**: 严禁 Worker 在落款字段返回首段授权长句。
  4. **DOM 写入物理强洗与正则熔断 (`fill_docx_proposals_in_dom`)**: 在写盘前若检测到名称字段仍被填入长句，底层强行用正则捕获出纯公司全称进行覆写。
- **单元测试**: 新增 `TestCheckShortFieldTextOverflow`，测试全量 31 项通过。

### 5. Review Agent 智能化 ReAct 大脑与实权修正架构重构 (`bid_filler_agent.py`)
- **核心架构升级**: 彻底改变 Review Agent 仅在事后做只读总结的边缘化状态，将其重构为**在写盘前拥有实权修正工具 + 数据库直查工具的终审 ReAct 智能大脑**。
- **全新决策工具箱**:
  1. `fix_proposal_tool(path, new_proposed_text, reasoning)`: 实权修正工具，审查 Agent 可根据智能推理与真值核对，自主修改任何错误提案。
  2. `reject_proposal_tool(path, reason)`: 拒绝工具，自主剔除无效或错挂提案。
  3. `get_all_bid_db_tools()`: 赋予审查 Agent 数据库直查权限（直查公司档案、项目元数据、财务报价），在怀疑数据错漏时直接查库取真值修正。
- **全新工作流**: `Worker Proposals -> 规则初筛诊断 -> 智能 Reviewer ReAct Agent (推理+查库+实权修正) -> 最终写盘引擎 -> 二次遗漏扫描`。

### 6. Supervisor 章节分类强约束与调试前缀排除清理 (`bid_filler_agent.py`)
- **问题场景**:
  1. 为什么后续章节没有被填写： Supervisor 之前的 Prompt 未限制分类边界，导致其误把带有`格式`后缀的格式章节（如 `二、投标函格式`、`三、开标一览表`）划分为 `skip` / `needs_writing`，导致 Worker Agent 在派发阶段跳过了对后续所有章节的填报。
  2. `封面段落原文：` 标签前缀误判：`_extract_prefix_from_text` 未能识别调试辅助词，将其误当成段落标签前缀拼到了 Word 中。
- **修复措施**:
  1. **Supervisor 章节分类硬规约**: 在 `analyze_chapters` 中下达强约束，规定《投标文件格式》模版中所有包含下划线、占位符或表格的章节，**必须分类为 `needs_fill` 或 `needs_data`**，严严禁误判跳过。
  2. **调试前缀排除清理**: `_extract_prefix_from_text` 增加对 `段落原文：` 等检索打印词的过滤，防止污染 Word 段落文本。

### 8. DOM 写盘原位切片替换与原文绝对保护算法升级 (`bid_filler_agent.py`)
- **问题根因分析**: 过去 DOM 填报引擎在遇到无已知前缀标签的嵌入型段落槽位时，粗暴使用了 `p_elem._element.clear_content()` 清空整段，导致将占位符前后的所有法律声明与格式模板汉字全部擦除（即出现“丢失原文”现象）。
- **原位切片槽位替换算法 (In-place Slot Sub-Replacement)**:
  1. 通过正则匹配精准定位段落内部的 `____`（下划线占位符）或 `[占位符]` 字符串。
  2. 精确切片拆分为：`[前文模板文本, 填入纯值, 后文模板文本]`。
  3. 前文与后文以普通格式（无下划线）物理留存写入，只有填入的纯值施加 Word 原生下划线修饰。
- **效果与测试**: 实现了占位符前后模板文字 100% 物理保留，彻底根治丢字、丢话、丢原文问题。新增单元测试 `test_fill_docx_proposals_inplace_sub_replacement_preserves_surrounding_text` 验证通过，全量 32 项测试通过。

### 13. DOM 越界路径预校验与 OfficeCLI 原子报错撤回修复 (`bid_filler_agent.py`)
- **根因死穴抓获**:
  - 为什么之前 273 处改动成功，却因为唯一 1 处表格合并列路径越界报错（如 `/body/tbl[2]/tr[20]/tc[2]/p[1]` 处不存在 `tc[2]`），导致 OfficeCLI 输出 `exit code 1` 并触发 atomic 全盘撤回（`atomic: no changes were applied`）。
  - 这直接造成了全书 273 处填好的表单全部被放弃恢复原样，只留下个别页面生还的假象。
- **双重金刚不坏防线**:
  1. **写前 DOM 路径预拦截 (Path Pre-Filter)**: 批量写入前使用 `_find_paragraph_by_path` 逐条过滤不存在的越界 Path，物理剔除导致 OfficeCLI 崩溃的坏路径。
  2. **OfficeCLI 异常平滑无缝降级 (Graceful Fallback)**: 若底层 OfficeCLI 抛出未预期错误，系统自动捕获并无缝平滑切换到纯 Python `fill_docx_proposals_in_dom` 刷盘，保住其余 273 处数据 100% 成功刷入 Word！

### 15. 正文段落占位符超强正则拓展与智能切片插值重构 (`bid_filler_agent.py`)
- **死穴破获**:
  - 之前《投标函》正文中的 `____号招标文件`、`______（姓名和职务）`、`______（投标人的名称）` 未能被单一下划线正则覆盖，导致误入 `else` 防覆写分支；
  - 旧逻辑在 `else` 分支因 `len(real_text) > 20` 成立而触发无脑 `continue` 跳过，导致正文段落槽位被放弃修改保留了空白下划线！
- **四重重构解法**:
  1. 拓展 `slot_pattern` 超强正则，全面捕获 `1+` 下划线、全角下划线 `＿`、`（姓名和职务）` 与 `（投标人的名称）` 等填报说明括号。
  2. 消除对 `（盖章）` 标签修饰词的误切，保留标签前缀完整性。
  3. 重构无显式下划线段落的写入逻辑：若未匹配到 `___` 且未包含填报值，在句尾安全追加填报值并施加下划线修饰，绝对不再无脑 `continue` 放弃写入。
  4. 测试集 33/33 PASSED 验证通过。
