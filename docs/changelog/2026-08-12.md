# 2026-08-12 变更日志

## MinerU 解析失败自动重试机制 (Bid Document & MinerU Retries)

### 变更背景
在智能评标流程中，解析投标文件等关键 PDF/Word 文档时，若网络抖动或 MinerU 在线 HTTP API 瞬时异常导致解析失败，系统此前直接抛出异常或触发降级，未给主引擎重试机会。

### 核心修改
1. **`MinerUParser` 重试逻辑升级** ([mineru_parser.py](file:///d:/Myproject/bidding_sys/backend/app/services/parsers/mineru_parser.py)):
   - 在 `parse()` 方法中新增 `max_retries: int = 2` 参数，默认最多重试 2 次（包含首次尝试共计最多 3 次）。
   - 重试时自动使用区分后缀的 `task_id` (`{base_task_id}_retry_{attempt}`)，防止云端 API 状态冲突或缓存失败。
   - 每次重试前增加 2 秒缓冲时间，并记录警告日志 (`logger.warning`)。
   - 只有在重试全部耗尽后，才抛出 `RuntimeError` 异常。

2. **`ExtractorService` 调用集成** ([extractor_service.py](file:///d:/Myproject/bidding_sys/backend/app/services/extractor_service.py)):
   - 在 `parse_and_chunk` 中明确传入 `max_retries=2`，在 MinerU 主引擎重试 2 次均失败后，再顺畅触发灾备保险开关切换至 DoclingParser 备用引擎。

3. **单元测试补充** ([test_mineru_service.py](file:///d:/Myproject/bidding_sys/backend/tests/unit/test_mineru_service.py)):
   - 新增 `test_mineru_parse_retry_success`: 模拟前两次解析失败、第 3 次重试成功的情况。
   - 新增 `test_mineru_parse_retry_exhausted_raises`: 模拟连续重试耗尽后抛出 `RuntimeError` 的边界场景。

### 验证情况
- 运行 `pytest backend/tests/unit/` 和 `pytest backend/tests/api/` 全部测试项通过 (11 unit tests, 28 api tests passed)。

## MinerU 超长 PDF (>200页) 自动切片解析与无缝合并 (MinerU Large PDF Auto-Chunking & Merging)

### 变更背景
MinerU 官方 HTTP API 存在单次请求 200 页物理上限限制，直接解析数百页的超长投标文件 PDF 会发生拒收或解析失败。

### 核心修改
1. **`MinerUParser` 内置拆片与无缝拼接机制** ([mineru_parser.py](file:///d:/Myproject/bidding_sys/backend/app/services/parsers/mineru_parser.py)):
   - 新建静态方法 `_get_pdf_page_count`：基于 C 引擎 `PyMuPDF (fitz)` 读取物理页数。
   - 新建静态方法 `_split_pdf_into_chunks`：当 PDF 页数大于阈值 `max_pages_per_chunk=180`（预留安全缓冲区）时，自动将其切割为 $N$ 个连续页码的子 PDF 文件。
   - `parse()` 方法重构：
     - 若为超长 PDF，自动触发多分卷并发调度流程，每个分卷均独立享受 2 次失败重试机制。
     - 解析完成后无损顺序拼接各分片的 Markdown 成果，注入 Chunk 页码注释标记。
     - 自动清理 `split_temp` 临时分卷文件，并将合成结果物理落盘为完整 `output.md`。

## FastAPI 事件循环阻塞修复 (Event Loop Non-Blocking Optimization)

### 变更背景
在触发 AI 打分 (`/api/v1/bid-scorer/score`) 或文档轻量解析等长耗时 CPU/IO 任务时，因为 API 端点使用了 `async def` 声明且在内部直接同步调用了 LangGraph / LLM / RAG 等 CPU 及同步 HTTP 请求，导致 FastAPI 的主 asyncio 单线程事件循环 (Event Loop) 被长时间独占阻塞 (30~180 秒)。在此期间，前端用户切换至其他页面发起的任何数据查询请求均无法被响应。

### 核心修改
1. **`bid_scorer.py` 端点异步线程池化** ([bid_scorer.py](file:///d:/Myproject/bidding_sys/backend/app/api/endpoints/bid_scorer.py)):
   - 引入 `from fastapi.concurrency import run_in_threadpool`。
   - 对 `/score` (AI 打分)、`/upload-bid` (投标文件解析)、`/chunks/{document_id}/batch-update` (切片批量标注)、`/evaluate-ragas/{result_id}` (Ragas 评估) 及 `/rescore-category` (维度微调重算) 等同步长耗时操作，统一使用 `await run_in_threadpool(...)` 将其分发至 Starlette 后台工作线程池中异步执行。
   - 解除主事件循环阻塞，使 FastAPI 能在打分后台进行的同时实时响应前端任何页面的查询请求。

2. **全量 API 模块巡检与异步线程池化** ([analysis.py](file:///d:/Myproject/bidding_sys/backend/app/api/endpoints/analysis.py), [bid_generator.py](file:///d:/Myproject/bidding_sys/backend/app/api/endpoints/bid_generator.py), [docx_debug.py](file:///d:/Myproject/bidding_sys/backend/app/api/endpoints/docx_debug.py), [mineru.py](file:///d:/Myproject/bidding_sys/backend/app/api/endpoints/mineru.py)):
   - **`analysis.py`**: 在 `reextract_domain` 重新提取端点中，将开标一览表生成 (`generate_opening_summary_node`)、成本测算 (`cost_node`)、资质盘点 (`analyze_qualifications_node`)、草稿起草 (`writer_agent_node`) 及元数据工具调用 (`tool_func.invoke`) 全部包裹为 `await run_in_threadpool(...)`。解决在重新提取任何字段时前端切页阻塞的问题。
   - **`bid_generator.py`**: 在 `extract_and_download_bid_format`、`fill_and_download_bid_format` 及 `trigger_human_like_bid_filling` 中，将 Word 响应格式提取导出与 Agent 标书填报全流程通过 `run_in_threadpool` 提交后台执行。
   - **`docx_debug.py`**: 对 DOM 编辑、修订痕迹接受、目录插入、隐私清洗、批注剥离等 Word 物理文件 CPU 节点操作包装 `run_in_threadpool`。

## 标书撰写控制台前端"闪一下就结束"及"无限卡死"SSE 生命周期双向修复 (Agent Audit Page SSE Lifecycle & Completion Fix)

### 变更背景
在【标书生成与撰写控制台】点击"启动 Agent 全自主撰写"后，存在两个严重的时序与判断 BUG：
1. **启动闪退**：前端页面上的 Agent 控制台闪一下就立刻回到 `STANDBY` 状态，看不到实时的 Worker 卡片弹增或 SSE 推流进度。
2. **无限卡死**：如果顺利进入了实时监听，当所有后台 Worker 都已完成执行且日志刷盘 (`status="success"`) 后，前端依然显示"AI 团队全自主撰写中..."，计时器无限跳动不停止。

### 根因分析
1. **启动闪退根因**：`handleStartFilling` 函数中 `POST /agent-fill-bid-format` 是一个**瞬间返回**的接口（仅启动后台线程），`await postPromise` 几乎立刻 resolve。`finally` 块在后台线程**刚刚开始**时就执行了，提前关闭了 SSE 连接并重置了 `isGenerating`/`isLivePolling` 状态。
2. **无限卡死根因**：后端 `/stream-logs` (SSE) 在判断 `is_completed` 时，其 `has_in_progress` 变量错误地遍历了**数据库中所有的历史全量日志记录** (`logs`)。因为日志系统是追加式的，包含最初始始化的 `in_progress` 记录，这导致不论最新状态如何，系统永远误判为“还有任务正在进行中”。

### 核心修改
1. **SSE 关闭逻辑从 `finally` 移至 `catch`** ([AgentAuditPage.tsx](file:///d:/Myproject/bidding_sys/frontend/src/pages/AgentAuditPage.tsx)):
   - 将 `setIsGenerating(false)`、`setIsLivePolling(false)` 和 `eventSourceRef.current.close()` 从 `finally` 块移至 `catch` 块中，仅在请求失败时才执行清理。
   - 正常情况下由 SSE `onmessage` 回调中已有的 `is_completed` 判断逻辑自然控制生命周期关闭。
2. **POST 成功后提示语修正**:
   - 将 POST 成功后误导性的"🎉 标书全自主智能撰写完成！"改为准确的"⚡ Agent 团队后台全自主撰写已启动，正在通过 SSE 实时推流监听进度..."。
3. **精准的 `has_in_progress` 状态映射判定** ([bid_generator.py](file:///d:/Myproject/bidding_sys/backend/app/api/endpoints/bid_generator.py)):
   - 移除了对全局历史大数组 `logs` 的 `in_progress` 暴力扫描。
   - 变更为对利用 `seen_chapters` 已经去重完毕、仅代表**每个章节卡片绝对最新状态**的集合 `worker_items` 数组进行扫描。使得 SSE 能够 100% 精准在所有子节点流转到 `success` / `failed` 瞬间返回 `is_completed: true`，彻底消除死循环卡挂问题。
