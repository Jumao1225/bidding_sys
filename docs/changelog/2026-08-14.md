# 改动日志 (Changelog) - 2026-08-14

## 修复《投标报价分析表》未填与表格数据列对齐问题 (全行业通用无硬编码架构)

### 1. 问题背景
- 在标书填报生成时，存在两个核心问题：
  1. 《投标报价分析表》整表未填（18 行数据行为空）；
  2. 《常用零件及耗材报价表》中数据列向左整体错位，产品名称被填入序号列，规格型号错入产品名称列，单价列留空。

### 2. 根本原因与架构重构
- **Worker 响应解析 (`_parse_proposals`)**：Worker 输出前置的数据来源说明表格（如 `| 数据项 | 检索结果 | 说明 |`）干扰了提案提取，导致真实的 `/body/tbl[2]` 表格数据提案丢失。已升级为基于 XPath DOM 语法的通用结构提取，彻底杜绝非写盘明细干扰。
- **纯 ORM 直查引擎 (`build_dynamic_matrix_for_header`)**：移除所有硬编码同义词词典，Worker LLM 探查实际表头后自主将表头映射为 ORM 字段名（含 `__INDEX__` 与 `__BRAND_SPEC__`），底层仅做确定性物理字段直查装配，实现全行业天然通用。
- **DOM 表格原位写盘 (`fill_docx_proposals_in_dom`)**：原生支持 `python-docx` 表格原位填报，自动探测模板预置空白数据行并优先原位覆盖，智能保护末尾固定非空行（如投标总报价、交货期限等落款汇总），严格保证列数对齐与序号注入。
- **全方位去硬编码**：清理了 `_extract_prefix_from_text`、`supervisor_audit_node`、表格结构分析中的硬编码关键词列表，全部转为结构化正则与文档特征解析。

### 3. 测试覆盖

## 修复 Worker 超时导致章节零写盘与 Supervisor 假通过未闭环行动问题

### 1. 问题定位
- 当个别 Worker（如《投标配置及分项报价表》）遇到 API 网络超时（`Request timed out`）时，旧版系统无自动重试机制直接宣告失败；
- Supervisor LLM 仅在文本回复中总结了“失败 1 项需人工关注”，而没有自动补发或触发代码层重试；
- `supervisor_audit_node` 仅通过正文正则扫描，未能识别空表格，导致误判通过，未能触发 LangGraph 条件边重修路由。

### 2. 核心架构修复
- **Worker 级网络容错自动退避**：在 `run_chapter_worker` 中引入最大 3 次自动重试与指数退避，遇到 Timeout/网络波动自动重发。
- **Supervisor 零写盘 (Zero-Write) 强制拦截**：在 `supervisor_audit_node` 中比对全量计划章节与实际产出提案章节，若发现核心章节零提案产生，强制判定 `audit_passed = False` 并打回重试。
- **DOM 表格 DB 直查双保险自愈**：在 `fill_docx_proposals_in_dom` 中，若遇到 Worker 产生表格路径但缺少 2D JSON 矩阵的情况，底层自动从数据库直查装配 16 项 BOM 矩阵，彻底杜绝空白表格。

## 投标配置及分项报价表（Table 2）与耗材报价表（Table 3）跨列分发与路径自愈修复

### 1. 深度根因诊断
- **现象**：Table 2《投标配置及分项报价表》中，第 18 行（总报价大写）和第 19 行（交货期限）成功填入，但第 1~17 行（BOM 设备清单）全部为空白；
- **根因剖析**：
  1. **Markdown 表格路径范围字符截断**：报价 Worker 为了表达整行 9 列填充，在总结表格中书写了形如 `/body/tbl[2]/tr[2]/tc[1..9]/p[1]` 的范围路径。原路径提取正则遇到 `..` 时发生截断，提炼出了缺失右括号的残缺路径 `/body/tbl[2]/tr[2]/tc[1`；
  2. **节点定位正则严苛**：`_find_paragraph_by_path` 过去严格要求 `tc[\d+]` 且必须闭合 `]`，遇到残缺的 `tc[1` 时匹配失败返回 `None`，导致全量 16 项 BOM 提案被跳过；

  4. **分隔符支持不全**：耗材 Worker 输出了 `1｜直流电缆｜...`（中文竖线 `｜`），原逻辑仅检测斜杠 `/`。

## 通讯地址与公文署名中文对齐标签被切断及前缀重复修复

### 1. 深度根因诊断
- **现象**：在《投标函》的通讯地址与署名栏中，出现了以下异常排版：
  - `邮邮    编：[待补充: 邮政编码]编：`
  - `电电    话：028-85123456话：`
  - `传传    真：[待补充: 传真]真：`
  - `投标单位代表姓名（签字）：投标单位代表姓名（签字）：李四`
  - `投标单位名称：投标单位名称：四川石楠建设工程有限公司`
  - `日日    期：2026年06月30日期：     年      月     日`
- **根因剖析**：
  1. **槽位正则误伤中文对齐空格**：在中文公文排版中，双字标签常在中间插入 2~4 个空格（如 `邮    编：`、`电    话：`、`日    期：`）。过去的槽位正则 `slot_pattern` 中包含 `\s{2,}`，直接匹配了标签字符中间的对齐空格，将 `邮    编：` 切割成了前缀 `邮` 和后缀 `编：`，导致填入值被夹在中间形成重复与断裂；
  2. **前缀剥离与写入机制不彻底**：当 Worker 提交了带完整属性标签的句子（如 `投标单位代表姓名（签字）：李四`）时，单槽位分支在写入时再次补加了一遍原前缀，导致标签重复出现两次。

### 2. 核心架构修复与双重守护
1. **槽位正则精确化约束 (`slot_pattern`)**：
   - 移除无条件 `\s{2,}`，限定仅匹配冒号后的填报空格 `(?<=[:：])\s{2,}` 或末尾空格 `\s{2,}$`，**严禁匹配中文标签词汇内部的排版对齐空格**。
2. **冒号标签引导行优先判定与前缀自动剥离 (`fill_docx_proposals_in_dom`)**：
   - 增加前置判定：识别段落开头的 `([^:：\n]{2,25}[:：])` 标签；
   - 自动检测并剥离 `proposed_val` 中携带的重复前缀（无论是严格字符还是带空格变体）；
   - 分离构建 Run 1（标准标签原文，不加下划线）与 Run 2（纯数据值，正文小四宋体加下划线），输出 100% 干净标准的公文排版：
     - `地    址：四川省成都市高新区天府大道北段128号`
     - `邮    编：[待补充: 邮政编码]`
     - `电    话：028-85123456`
     - `传    真：[待补充: 传真]`
     - `投标单位代表姓名（签字）：李四`
     - `投标单位名称：四川石楠建设工程有限公司`

## 修复分项报价表与技术偏离表空白问题（Table Guard 纯动态自愈引擎，零硬编码）

### 1. 深度根因分析
- **现象**：在实际生成文档中，《开标一览表》、《常用耗材表》、《实质性对照表》、《商务偏离表》均已完整填入，但《五、投标配置及分项报价表》（Table 2）和《十一、技术要求响应及偏离表》（Table 6）全为空白；
- **根因剖析**：
  1. **Worker 超时（Timeout）与无保底**：报价 Worker 在并发进行 16 行长矩阵提取时遭遇大模型 API 网络请求超时（`Request timed out`），Worker 异常退出，未产生有效提案；
  2. **技术偏离表虚假概括行**：技术偏离 Worker 输出了概括行路径 `tbl[6]/tr[2]`，被安全过滤拦截，导致数据未能落盘到具体单元格；
  3. **系统缺乏底盘表格自动对账自愈（Zero-Timeout Fallback）**：写盘引擎在遇到 Worker 超时或提案异常时，直接将空白表格放行写盘。

### 2. 核心架构修复与无硬编码动态自愈
1. **全表健康度巡检与纯动态保底对账引擎 (`_heal_empty_pricing_and_deviation_tables`)**：
   - 在 `fill_docx_proposals_in_dom` 写入 Word 之前，增加底盘表格健康度巡检：
   - **分项报价表动态对账**：检测到数据行全空时，纯动态通过当前 `document_id` 从 `CostEstimate` 查库提取真实 BOM 列表，自适应识别当前表格的表头列名并生成动态矩阵写入各行各列；同时从 `FinancialMetadata` 与 `TimelineMetadata` 动态计算总价小写、大写金额与工期并补齐表尾；
   - **技术偏离表动态对账**：检测到数据行全空时，纯动态从 `EngineeringMetadata`（主要设备清单与强制性标准）提取真实技术指标，自动生成标准 5 列逐项合规闭合响应（序号 1~N 递增、招标文件原文要求、服务承诺、无偏离）；
2. **100% 杜绝硬编码与业务数据泄露**：
   - 彻底清理所有写死或硬编码的具体项目品牌、金额或厂商，所有字段均由 ORM 实体字段反射与动态 SQL 驱动，天然适配任何行业与任何标书模板；
3. **安全自愈边界保护**：
   - 仅当表格的所有数据行确实全部为空白时才启动自愈，若已有 Worker 填入的高质量实质性条款，绝对安全保留并不予覆盖。
